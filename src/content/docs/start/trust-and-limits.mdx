The model is simple to state and easy to over-read. A verified human is
accountable for an agent; the broker proves that and records what was accepted.
A provider may additionally publish a broker-issued provider verification
credential so an agent can check who it is before signup. That check records
identity, not safety, and it does not police what an agent does after signup.

## The liability chain

```text
verified human owner
  -> master delegation agreement (one per human)
  -> delegated ToS acceptance (exact text, hash, timestamp)
  -> signed assertion (agent, human, acceptance)
  -> optional provider verification credential (RP attestation)
  -> provider account (created or resolved by the provider)
```

Each link is recorded. The human signs the master agreement once. Every service
acceptance is a separate durable event with the terms URL, the terms hash and the
master agreement version. The assertion carries the acceptance forward, so the
provider does not have to trust a self-declared claim.

What the chain does not do: it does not transfer liability to the broker, and it
does not make the provider a party to the master agreement. The provider's own
terms govern the provider's account.

## Assertion verification is permissionless

Anyone can verify a Contract A assertion against the human broker's public JWKS.
No account, SDK, shared secret, or broker call is required. This is the base
conformant flow and it has not changed.

A provider account is a different thing. It is required only to be a verified
provider, issue authenticated receipts, or report abuse with standing. It is not
required to accept assertions, and attestation issuance is not plan-gated: an
active provider with a verified origin and an active key can issue.

## What provider verification adds

A provider may publish an optional `attestation` object in its discovery
document. The public term is **provider verification credential**: a compact JWS
issued by the provider's broker (Broker B) that binds:

- the provider's canonical origin;
- its discovery `audience`;
- its provider identity and contact;
- an assurance level (`domain` or `entity`);
- its public signing keys.

Discovery names a stable **source** and never carries the token itself:

```json
{
  "attestation": {
    "mode": "broker",
    "uri": "https://agentregistrar.dev/api/broker/provider-verification?origin=https%3A%2F%2Fprovider.example&audience=example"
  }
}
```

- `mode` is exactly `broker` or `provider`.
- `uri` is a stable, absolute HTTPS URL with no credentials and no fragment.
  `http://localhost` and `http://127.0.0.1` are the development exception.
- The object is optional. Absence is conformant and means **unverified**.
- The old embedded `rp_attestation` discovery field is removed. A document that
  still carries it is **non-conformant**; it is not a fallback.

Both modes serve the same source document at `attestation.uri`:

```json
{ "attestation": "<compact JWS>" }
```

The response is `application/json`. Additional fields are ignored. A raw JWT
body is rejected. The envelope is not signed, so the JWS is the only trust
anchor.

An agent or broker verifies the token locally against Broker B's JWKS, checking
the signature, `typ`, `alg`, `kid`, `iat`/`exp` with 60 seconds of clock skew,
`rp.origin` against the origin of the discovery document actually fetched, and
`rp.audience` against `discovery.audience`. The trusted-Broker-B check happens
before any JWKS fetch. Local verification does not need a status call.

The credential is **optional**. A conformant discovery document without it is
**unverified**, never invalid. Absence, expiry, a bad signature, an untrusted
broker, and an unavailable source are different results, and the
[validator](/agent-identity/v1/validator/) reports conformance and attestation
verification separately.

## The two publication modes

One mode is chosen per origin and audience pair. Switching modes is a
configuration change that reissues the attestation and updates discovery; it is
not a per-request choice.

### Broker-managed (default)

The broker hosts and renews the token at a stable verification endpoint:

```text
GET /api/broker/provider-verification?origin=<encoded>&audience=<audience>
```

The provider publishes that full URL as `attestation.uri` and changes nothing
else. There is no cron, no renewal job and no redeploy: the broker renews on
demand when 12 hours or less remain, so a `200` never carries an expired token.
The URI is stable across renewals.

The broker-managed lookup **is the status check**. There is no separate status
call in this flow. A positive answer may be cached for at most five minutes and
never past `exp`; a negative answer is never cached. The five-minute bound is
also the revocation lag: a suspension stops new lookups within five minutes, not
instantly.

| Broker answer | Meaning | Client action |
| :--- | :--- | :--- |
| `200` with `{attestation}` | Current and active | Verify locally, then proceed |
| `400 invalid_request` | Malformed query | Fix the request |
| `403 provider_suspended` | Provider or origin suspended | Reject |
| `404 attestation_not_found` | Unknown pair, wrong mode, unverified origin, or no attestation | Unverified under `verify`/`strict`; show unverified under `no_verify` |
| `410 attestation_revoked` | Provider or attestation revoked | Reject |
| `429 rate_limited` | Rate limited; `Retry-After` is set | Retry after the advertised delay |
| `5xx` (`503 broker_unavailable`) | Broker unavailable | Use a cached positive answer inside five minutes, or fail per policy |

A typed broker answer is a verification result. It is never a conformance
failure and never makes the discovery document non-conformant. The endpoint
accepts a provider origin and audience only; no agent or human identifier is
sent to it.

### Provider-managed (opt-in)

The provider hosts the source document at a stable URL on its own origin or a
subdomain of it, and the broker does not proxy, cache, or publish the token.

- Register the stable HTTPS source URL. A third-party host, including a CDN, is
  rejected: the URI host must be the discovery origin or a subdomain of it.
- Renew through `POST /api/provider/v1/attestation` on the 12-hour target
  against the 24-hour expiry, and write the returned `attestation` JWS into the
  source document. Keep serving the current token until the new one is
  published; never serve an empty document.
- `exp` is the **revocation bound**. A client accepts the token until `exp` plus
  skew, so a broker suspension or revocation may not be visible until the token
  expires. This mode is not instant revocation.
- A client may reuse a fetched source response for at most five minutes and
  never past `exp`.

A source that is unreachable or malformed is `unavailable` or `invalid`, never
"unsafe": it is a verification result about evidence, not a conformance verdict.

## Assurance levels

| Level | What was checked |
| :--- | :--- |
| `domain` | Automated control of the origin through an HTTPS well-known file or a DNS TXT record. |
| `entity` | An operator reviewed legal-entity evidence: legal name, registry/VAT id, and official contact, in addition to the origin check. |

Both levels count as `verified` for policy. The level is recorded and displayed.
It is not a ranking and there is no `enhanced` level.

## Trust is policy, not cryptography

A valid credential says "this broker vouches for this origin and audience at this
time". Whether that broker is trusted is a local policy decision. Trust is not
transitive: trusting Broker B to attest a provider does not make B's other
statements authoritative, and it says nothing about the provider's safety,
uptime, solvency, or conduct.

The broker default plus the human owner's overrides resolve trust. A human can
mark a broker `trust` or `distrust`; distrust wins. Agents inherit their human's
policy; there is no per-agent trust list.

Policy is separate from verification status. The values are `no_verify`,
`verify` (the default), and `strict`:

| Policy | Verified | Unverified | Untrusted broker | Invalid or expired | Unavailable | Suspended |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| `no_verify` | proceed | proceed, shown as unverified | proceed | proceed | proceed | proceed |
| `verify` | proceed | `rp_unverified` | `rp_broker_untrusted` | `rp_attestation_invalid` / `rp_attestation_expired` | `rp_broker_unavailable` | `rp_suspended` |
| `strict` | proceed, broker-managed only | `rp_unverified` | `rp_broker_untrusted` | `rp_attestation_invalid` / `rp_attestation_expired` | `rp_broker_unavailable` | `rp_suspended` |

- `no_verify` never turns a verification result into a refusal. A present
  credential is still verified for display and recorded.
- `verify` requires a valid attestation and accepts either publication mode.
  A `404 attestation_not_found` is `unverified`.
- `strict` requires a valid **broker-managed** attestation and rejects a
  provider-managed source with `rp_attestation_mode_not_allowed`. It also
  rejects a caller-supplied discovery document with
  `discovery_source_not_allowed`.
- `blocked` is a separate human action, not a fourth mode. `blocked = true`
  refuses with `rp_blocked` after discovery resolution and before any
  attestation-source fetch, whatever the mode and whatever the status.

`verify` and `strict` are always enforced. There is no advisory policy and no
`enforced` field. The old `allow`, `warn`, `require`, and `block` policy values
are removed, with no aliases.

## Provider verification is identity, not safety

"Verified" means a broker checked an origin and, at entity level, reviewed
legal-entity evidence; policy accepted the credential. It does **not** mean safe,
approved, endorsed, audited, trustworthy, solvent, or reliable. A verified
provider can still misbehave. Verification reduces impersonation risk; human
reports, expiry, revocation, and policy remain the controls.

The registry shows the recorded status at `checked_at` and labels it a snapshot.
It is not a live status feed and a listing is not an endorsement. The live
VaporCloud reference entry carries a domain-level snapshot checked on
2026-10-26; it records the broker's identity check, not product safety or
conduct.

## Receipts and proof sources

A signup receipt is signed by the provider's own key, named by
`service.attestation_jti` and `service.key_id`. It carries no `exp`: a receipt is
a historical fact. The receipt is valid when `iat` and `signed_up_at` both fall
inside the named attestation's validity window, even if the broker ingests it
after the attestation expires. The broker keeps the verified attestation snapshot
and never substitutes a newer attestation or a broker-signed fallback.

There are four proof sources:

| Proof source | Meaning |
| :--- | :--- |
| `rp_callback` | Tier 1: the provider posted the RP-signed receipt to Contract F. |
| `rp_signed` | Tier 2: the agent recorded the same RP-signed receipt through `identity_record_signup`. |
| `agent_self_reported` | No provider signature. Weaker and visibly marked. |
| `legacy_broker_signed` | A pre-v1.2 row. Historical and unverified. |

Tier 1 and Tier 2 carry the same proof. A self-report is not verified. `exp` on a
legacy receipt is ignored.

Contract F and authenticated abuse reporting still use the request-body field
`rp_attestation` for the exact historical attestation. Only discovery removed it.

## Authenticated abuse reporting

A provider with a current attestation can send `POST /api/broker/report-abuse`
with `{rp_attestation, report}`, where `report` is a compact JWS with a
five-minute freshness window. The broker checks broker trust before any JWKS
fetch, then verifies the report signature with the named key. A report is
`verified` only when it is linked to a signup with `proof_source` `rp_callback`
or `rp_signed` and a verified attestation. Only a verified, receipt-linked report
can request a protective suspension pending operator review, and every accepted
report opens a case.

An unlinked, self-reported, or legacy-linked report is `unverified`: it opens a
case but does not suspend. Unauthenticated legacy posts get `401
unauthenticated_report`. Reporting from a human about a provider is portal-only
(`POST /api/broker/report-provider`) and updates that human's trust/policy; it
does not adjudicate a dispute.

## Status at signup, current status, and revocation

The ledger shows two separate things:

- **status at signup**: the verification event recorded for that signup;
- **current status**: the latest recorded status for the same origin and
  audience, with local overrides.

Current status is historical, not a live query. It carries `checked_at`. Local
provider suspension/revocation, local attestation suspension/revocation, or
snapshot expiry can override the label.

Where the current answer comes from depends on the mode:

- **Broker-managed:** the broker lookup is the status check. A suspension is
  visible within five minutes at most and no new token is issued.
- **Provider-managed:** expiry is the revocation bound. A suspension may not be
  visible until the token expires.
- The broker metadata still advertises a signed `attestation_status_uri`
  (Contract I), and the signed status is the durable record. Local verification
  does not require it.

Revocation affects new `identity_signup`/`identity_prove` calls and
identity-bound tool calls. It does not delete a provider account, invalidate an
assertion already handed over (which expires within five minutes), or reclaim
provider credentials. A human kill switch sets `revoked`. An operator protective
action sets `suspended`; the human cannot silently clear a suspension.

## Known gaps

These are limitations of `agent-identity-v1` and of this broker. They are stated
here so no page has to soften them.

1. **Unverified providers still exist.** A conformant provider can omit the
   optional `attestation` object. `no_verify` proceeds; `verify` and `strict`
   refuse. Choosing a provider is still a trust decision.
2. **Verification is not a safety review.** A malicious provider can obtain a
   `domain`-level credential by controlling an origin. `entity` adds reviewed
   legal-entity evidence, not honesty or product quality.
3. **The assertion discloses contact details.** Even with verification, the
   assertion gives the provider the agent address, the human's name and email,
   and the acceptance facts.
4. **Conformance is cheap.** The validator checks document shape and encoding,
   not intent, security posture, or business legitimacy.
5. **Revocation is bounded, not instant.** A broker-managed suspension stops new
   lookups within five minutes. A provider-managed suspension may not be visible
   until the token expires.
6. **Revocation is a broker control.** It cannot delete an account, invalidate a
   live assertion, or force a provider to stop serving the agent.
7. **Provider enforcement varies.** A provider may skip a check or never call the
   abuse endpoint. The protocol defines checks; it cannot make a provider run
   them.
8. **The broker is a single point of failure for minting.** If the broker is
   unavailable, no new assertions can be minted. Providers and existing accounts
   are unaffected.
9. **Email delivery is in the critical path.** The acceptance receipt, human
   forward, and provider verification mail depend on mail delivery. A failed
   ledger dispatch is retryable; the acceptance is already recorded.
10. **`human.verified` is verified email, not KYC.** Two broker accounts with
    different emails are two principals. The broker cannot merge them.
11. **No credential custody.** The broker cannot recover a provider credential,
    because it never stores one. Recovery is the provider's path.

## What we do not claim

- No SOC 2, ISO 27001 or equivalent attestation.
- No uptime SLA or availability target.
- No adoption, customer-count or revenue figures.
- No claim that the protocol prevents abuse, enforces revocation at a provider,
  or makes an agent or provider trustworthy.
- No claim that verification means safe, approved, endorsed, or audited.
- No legal advice. The master agreement and the provider terms are the legal
  documents; this site explains mechanics.

## Security and abuse contacts

Report a vulnerability in the broker, the protocol or this documentation to
`security@agentregistrar.dev`, the address published in the site footer. Reports
are handled on a best-effort basis; there is no bug bounty and no guaranteed
response time. Do not include live credentials, JWTs or personal data in a
report.

For documentation and specification defects, open an issue on
[the specification repository](https://github.com/agentregistrar/spec/issues).
For provider-side abuse, use the provider's own contact and, where it supports
it, the broker abuse endpoint.
