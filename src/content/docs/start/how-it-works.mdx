A brokered signup takes six steps. The human verifies once, binds an agent during browser OAuth consent, and lets the agent request a short-lived signed identity token for each service. The agent posts that token directly to the provider's signup API, and the broker records the terms acceptance and optional receipt in `/activity`.

## The six-step signup flow

<HandshakeDiagram />

The dashed lines mark three trust boundaries: human consent after step 1, broker token minting after step 3, and provider verification after step 5.

1. **Verify once (Human).** Sign in at [agentregistrar.dev/login](https://agentregistrar.dev/login) with GitHub, verify your email address with a six-digit code, and sign the Master Agent Delegation Agreement. This happens once per human account.
2. **Connect and bind an agent (Agent + Human).** Add `https://agentregistrar.dev/mcp` to your coding tool and complete OAuth 2.1 sign-in in your browser. On the consent screen, pick an existing active agent or create a new one (up to your active agent quota, default `2`). That binds the OAuth session to one specific agent identity and its `@agents.agentregistrar.dev` inbox.
3. **Fetch terms and mint a token (Broker).** When the agent calls `identity_signup` with a service URL, the broker fetches `/.well-known/agent-signup.json` and the provider's terms page (`terms.url`), hashes the exact bytes received, checks the provider's optional verification credential against your trust policy (`verify` by default), records the acceptance, emails a copy of the terms to your verified email, and mints a five-minute signed identity token. It returns a ready-to-send `signup_request`.
4. **Sign up directly (Agent).** The agent sends `signup_request` verbatim (`POST` to the provider's signup URL with `Authorization: Bearer <token>` and body `{}`). The broker does not proxy this request and never sees any API key the provider returns.
5. **Verify and create or resolve the account (Provider).** The provider verifies the signed token against the broker's public keys (JWKS), checks the issuer allowlist, audience, expiry, scopes, verified human flag, and accepted terms URL, and creates or resolves the account. On first creation, the provider returns its show-once credential (which the agent stores immediately), an optional signed receipt (`signup_token`), and an optional hash-pinned usage guide link (`context`).
6. **Record the receipt (Broker).** If the provider returned a `signup_token`, the agent calls `identity_record_signup`. The broker verifies the receipt and attaches it to the acceptance row in your `/activity` audit trail. Even when a provider does not issue a signed receipt, the terms acceptance from step 3 is already visible in `/activity`.

## Why terms are fetched and hashed by the broker

Providers host their agreement at a plain URL (`terms.url`) and publish a `terms.version`. At signup time, the broker fetches that URL directly and computes a SHA-256 hash of the exact response bytes.

- The agent cannot spoof or alter the terms hash it claims to have accepted.
- You receive an emailed copy of every accepted terms agreement at your verified email address, regardless of your `/settings` email forwarding preference.
- If a provider updates its terms later, its signup endpoint rejects assertions carrying an outdated terms URL or version, prompting a fresh acceptance rather than overwriting history.

## What the provider verifies

The provider inspects four groups of signed claims inside the five-minute token after verifying its signature against the broker's public JWKS:

| Claim group | What it proves | Key check at the provider |
| :--- | :--- | :--- |
| Token envelope (`iss`, `aud`, `jti`, `iat`, `exp`) | Issued by an allowed broker for this exact service within the last five minutes | `iss` in `issuer_allowlist`, `aud` equals discovery `audience`, not expired (up to 60s skew) |
| Agent (`agent.id`, `agent.name`, `agent.email`, `agent.harness`) | Which delegated agent is acting and where to email notices | Stable attribution key when keying accounts per agent |
| Human (`human.id`, `human.name`, `human.email`, `human.verified`) | Which verified human owner is accountable | `human.verified` must be `true`; stable key when keying accounts per human |
| Delegation (`delegation.accepted_rp_tos_url`, `accepted_rp_tos_hash`, `accepted_at`, `scopes`, `master_tos_version`) | Exact terms accepted, original consent time, and granted scopes | `accepted_rp_tos_url` matches current `terms.url`; `scopes` covers all `required_scopes` |

Providers should key accounts on `(iss, human.id)` for one account per human or `(iss, agent.id)` for one account per agent, never on email alone. See [Assertion claims](/protocol/assertion-claims/) for the full normative table.

## Where the agent inbox fits

Every agent gets a dedicated address (`<agent-slug>@agents.agentregistrar.dev`).

- **Terms copies:** always emailed to your verified human email and logged in `/activity`.
- **Provider emails and verification codes:** arrive in the agent inbox. The agent reads or polls for them with `inbox_read` (which automatically extracts standalone six-digit codes as `detected_otp`).
- **Forwarding control:** in `/settings`, you choose whether inbound agent emails forward to your human address (`all` by default, `legal_only`, or `off`). You can also view every message live in `/agents/[id]`.

## Revocation and retries

**What the kill switch stops.** Clicking **Revoke agent** in `/dashboard` or `/agents/[id]` immediately blocks that agent from minting new identity tokens or reading its inbox. An operator protective suspension (following a verified, receipt-linked abuse report) sets status to `suspended` and blocks new tokens and new OAuth connections until reviewed and restored by the broker operator.

**What the kill switch does not stop.** Revocation is a broker control, not a remote delete button on third-party infrastructure. It does not delete accounts a provider already created, revoke provider API keys you stored, erase recorded terms acceptances, or recall a token already handed to a provider (which expires within five minutes).

**Safe retries.** Calling `identity_signup` again with the same inputs while a token is unexpired reuses the exact same token and sends no duplicate email. After expiry, a new token references the same original acceptance timestamp. On the provider side, repeating a signup for an existing account returns `resolution: "resolved"` with no new credential.
