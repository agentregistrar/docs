Agent Registrar is an agent identity broker. A verified human signs one Master Agent Delegation Agreement; each connected agent gets its own identity and email inbox. When an agent signs up for a supported service, Agent Registrar records the exact terms accepted, emails a copy to the human, and issues a short-lived signed identity token the provider verifies directly on its own domain.

## Product, protocol, and broker

Three names appear across these docs. They are separate layers with clear boundaries:

| Layer | What it is | What it owns |
| :--- | :--- | :--- |
| **Agent Registrar** (the product) | The hosted service and Developer and Provider Portals at `agentregistrar.dev` | Human accounts, agent identities, inboxes, the `/activity` audit trail, trust settings, and per-agent kill switches |
| **Agent Identity Protocol** | The open Apache-2.0 specification (`v2.1.0`) | Discovery document format, signed identity token claims, optional signup receipts, and stable error codes |
| **Broker** | Any service implementing the broker role (Agent Registrar is the hosted broker) | Human email verification, short-lived token minting, acceptance records, the 4-tool MCP server, and agent inboxes |

The specification, validator, and documentation are Apache-2.0; the hosted broker codebase is private. Any broker that implements the open protocol can mint tokens that a conformant provider accepts, and any provider can verify tokens against public keys without a broker SDK.

## Four gaps brokered signup closes

Standard web signup forms assume a human is sitting at a browser. When an agent tries to sign up for an API or SaaS tool, four things break:

1. **Auditable terms acceptance.** An agent cannot click "I agree" in a way a service can audit later. With Agent Registrar, the human signs one master agreement, and every service signup fetches the provider's terms page, records a SHA-256 hash of the exact bytes, and emails a copy to the human.
2. **Accountable human owner.** A service needs to know which verified human stands behind a new account. The signed identity token carries the human's verified email status and stable identifier alongside the agent's identity.
3. **Reachable inbox.** A service needs an address for welcome mail, verification codes, billing notices, and abuse escalations. Every agent gets a dedicated `@agents.agentregistrar.dev` inbox that the agent can read and the human can inspect or forward.
4. **Abuse escalation and stop control.** A human needs a one-click kill switch to stop a misbehaving agent from minting new tokens, and a verified provider needs an authenticated path to report abuse so the broker can open a case and, for verified receipt-linked reports, apply a protective suspension pending review.

## What each party gets

- **Developers running agents** get a single remote MCP endpoint (`https://agentregistrar.dev/mcp`) with four tools (`identity_whoami`, `identity_signup`, `identity_record_signup`, `inbox_read`), one dedicated inbox per agent, emailed copies of every accepted terms agreement, a unified `/activity` audit trail, and a one-click kill switch per agent.
- **Service providers** keep their own domain, signup API, customer accounts, credentials, and pricing. They publish one discovery file and verify incoming signed tokens against public keys. Creating a free provider account in the Provider Portal is optional for verifying tokens, and recommended so default `verify` clients recognize your verified domain and so you can issue signed receipts or submit authenticated abuse reports.

## What this is not

- **Not a marketplace.** Providers host their own signup API on their own domain and keep the customer relationship, credentials, and product UX.
- **Not a credential vault or password manager.** Agent Registrar never sees, stores, or proxies provider API keys or passwords.
- **Not a payment or billing rail.** The protocol carries no wallet, card, or payment capability.
- **Not a provisioning API.** Brokered signup creates or resolves an account; vendor resources are created through the provider's own API after signup.
- **Not KYC or legal identity proofing.** A verified human owner means a verified email address, not government-ID KYC.
- **Not bot detection.** The protocol does not try to distinguish humans from scripts; it makes a verified human accountable for the agent.
- **Not a safety stamp.** A verified domain confirms domain control (or reviewed legal-entity evidence at the `entity` level). It never means a provider is safe, approved, or endorsed.
