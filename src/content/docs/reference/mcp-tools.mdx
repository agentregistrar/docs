The broker exposes eight tools over the Model Context Protocol (MCP) at `https://agentregistrar.dev/mcp`. Four manage the agent identity and four manage its inbox. This page is the lookup table: inputs, result keys, side effects, retry rules, error codes and one example per tool.

The normative contracts are elsewhere. Inputs and the two structured results are defined in `packages/shared/src/schemas/mcp-tools.ts`; the behavior is in the broker's tool modules. The [error reference](/reference/error-codes/) holds the code list, and the [broker HTTP reference](/reference/broker-http/) holds the transport and OAuth endpoints. This page links to both rather than repeating them.

## Endpoint and discovery

- URL: `https://agentregistrar.dev/mcp` (Streamable HTTP, JSON-RPC 2.0).
- Auth: OAuth 2.1 bearer access token (`mca_...`), sent as `Authorization: Bearer`. The token is bound to one verified human owner.
- Transport: one stateless handler per request. There is no session id to keep, and `POST` is the only method the tool flow needs.
- `initialize` reports `serverInfo.name` `agentregistrar`, version `1.0.0`, capabilities `tools` and `resources`, and the system instructions that describe the workflow.
- `tools/list` returns exactly eight tools.
- `resources/list` returns four static `text/markdown` resources. They repeat documented material for clients that cannot follow links; the pages they point at stay canonical.

```bash
export MCP_TOKEN="<the mca_ access token from your client's OAuth flow>"
curl -sS -X POST https://agentregistrar.dev/mcp \
  -H "Authorization: Bearer $MCP_TOKEN" \
  -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list"}'
```

The handler also accepts a POST with only `Accept: application/json` and defaults a missing `Content-Type` to `application/json`, so plain `curl` calls work. A request without a bearer token gets `401` with a JSON-RPC error code `-32001` and a `WWW-Authenticate` challenge; see the [transport errors](/reference/error-codes/#mcp-transport-and-gate-errors).

## Before you call

The transport gate runs before any tool:

1. The bearer token must resolve to an `mca_...` token row that is not revoked and not expired. Otherwise `401`, code `-32001`.
2. The token's human owner must be `active` and must have signed the Master Agent Delegation agreement. Otherwise `403`, code `-32003`.
3. The agent sub-identity must exist and be `active`. `identity_register` creates it; `identity_whoami`, `identity_prove` and the inbox tools resolve it and auto-provision a default one when the session has none.

A revoked agent fails at the tool layer with `agent_revoked`, not at the transport. Scope checks are per tool: `identity_prove` needs `tos:accept`, the inbox tools need `inbox:read` or `inbox:send`.

## How to read each entry

- **Purpose**: what the call is for.
- **Inputs**: the exact JSON Schema properties from `tools/list`, with type, required marker (`required`), default and constraint.
- **Result**: the keys the agent sees. `identity_prove` and `identity_record_signup` also register an `outputSchema`; the other six return a text JSON payload only.
- **Side effects**: what changes in the broker, including whether mail is sent.
- **Retry**: whether repeating the same call is safe, and what to change when it is not.
- **Errors**: the stable codes, linked to [Error codes](/reference/error-codes/).
- **Example**: `arguments` and the parsed result object. Response bodies are illustrative unless marked live; IDs and emails are synthetic.

A tool failure is not an HTTP error. It returns a normal JSON-RPC result with `isError: true` and the error envelope as text content:

```json
{
  "content": [
    {
      "type": "text",
      "text": "{\"error\":{\"code\":\"wait_timeout\",\"message\":\"...\",\"retryable\":true,\"side_effects\":{},\"next_step\":\"...\",\"docs\":\"agentregistrar://docs/error-recovery\"}}"
    }
  ],
  "isError": true
}
```

The `text` value is a JSON string: parse it before reading `code`. `message` is human-readable and may change; `code`, `retryable`, `side_effects` and `next_step` are stable.

## identity_register

Title: "Create or resume agent sub-identity". Registers the agent sub-identity for the authenticated session, or returns the one already bound to it.

**Inputs**

| Field | Type | Required | Default | Constraint and meaning |
| :--- | :--- | :-: | :--- | :--- |
| `name` | string | no | `opencode-agent` | `minLength: 1`. Display name; also the base of the email slug. A repeated call with the same name and harness for the same human reuses the existing agent. |
| `harness` | string | no | `opencode-v2` | `minLength: 1`. Harness identifier, stored on the agent and embedded in the assertion `agent.harness`. |

The input object is closed (`additionalProperties: false`).

Lookup order: the agent bound to this OAuth token first, then an agent with the same `name` and `harness` for the same human, then create. A token-bound agent wins, so a different `name` does not create a second identity in the same session.

**Result**

```json
{
  "id": "agt_01jdocsverify0000000000000",
  "name": "example-agent",
  "slug": "example-agent-0abc12",
  "harness": "opencode-v2",
  "email_address": "example-agent-0abc12@agents.agentregistrar.dev",
  "scopes": ["tos:accept", "signup:free_tier", "inbox:read", "inbox:send"],
  "status": "active",
  "created_at": "2026-10-21T10:00:00.000Z",
  "human_owner": {
    "id": "hum_01jdocsverify00000000000",
    "name": "Example Human",
    "email": "human@example.com",
    "master_tos_version": "2026-10-01",
    "verified": true
  }
}
```

`created_at` is present on `identity_register` and absent from `identity_whoami`, which is otherwise the same flat profile.

**Side effects and retry**

- Creates one `agents` row with the default scopes, a `<slug>@agents.agentregistrar.dev` address and `status: active`.
- Sends no email. The inbox address exists from registration; messages arrive later.
- Retry: safe and idempotent. Repeating the call returns the active agent.
- A revoked agent is not silently replaced: the call fails with `agent_revoked`.

**Errors**

| Code | Retryable | Meaning |
| :--- | :-: | :--- |
| `agent_revoked` | no | The resolved agent is revoked. Ask the human to review it, or register from a new session. |
| `internal_error` | yes | Unexpected broker or database failure. |

The human-account gates (`human_suspended`, `human_email_unverified`, `master_tos_unsigned`) are enforced by `identity_prove`; at the transport they appear as `403` code `-32003`.

**Example**

```json
{ "name": "example-agent", "harness": "opencode-v2" }
```

Live result keys on 2026-10-21, from an existing agent, were exactly `id`, `name`, `slug`, `harness`, `email_address`, `scopes`, `status`, `created_at`, `human_owner`.

## identity_prove

Title: "Accept ToS & mint identity assertion". Records the human owner's delegated acceptance of a relying party's terms and returns a signed Ed25519 assertion for that audience. This is the only tool with a legal side effect.

**Inputs**

| Field | Type | Required | Default | Constraint and meaning |
| :--- | :--- | :-: | :--- | :--- |
| `audience` | string | yes | - | `minLength: 1`. Exact case-sensitive `audience` from the relying party's discovery document; becomes `aud`. |
| `accept_tos_url` | string | yes | - | `format: uri`. `terms.url` from discovery: the URL a human can read. |
| `accept_tos_hash` | string | yes | - | Must equal `sha256:` plus 64 lowercase hex characters over `accepted_tos_text`. The broker recomputes and compares it; a mismatch fails before any side effect. |
| `accepted_tos_text` | string | yes | - | `minLength: 1`. The complete `terms.text` exactly as received. |
| `requested_scopes` | array of strings | no | `["tos:accept","signup:free_tier"]` | Every entry must already be held by the agent; the list is embedded in `delegation.scopes`. |
| `force_new` | boolean | no | `false` (absent) | Record a new consent event even when an acceptance for the same service and terms exists. |

The advertised JSON Schema for `accept_tos_hash` carries `pattern: "^sha256:"` only. The effective rule is stricter: the value must equal the recomputed digest, so a malformed hash can never match.

Gate order, all before any write: text-hash match, human active, human email verified, Master ToS signed, agent not revoked, `tos:accept` held, requested scopes held.

**Result**

| `assertion.issued_at` | ISO 8601 string | From `claims.iat`. |

### Behavior, reuse and side effects

- Irreversible: records one `tos_acceptances` row (a durable legal event) and dispatches one ToS Acceptance Ledger email to the agent inbox plus a forward to the human owner's verified address.
- An identical call while the stored assertion is unexpired returns the byte-identical JWT, same `jti`, same `exp`, and sends no new mail. `reuse.reason` is `existing_assertion`.
- After the assertion expires, a fresh `jti` references the same acceptance. `accepted_at` does not move. `reuse.reason` is `fresh_assertion_existing_acceptance`.
- `force_new: true` records a genuinely new consent event (`forced_new_acceptance`). A different `(audience, url, terms_hash)` does too (`new_acceptance`).
- The acceptance get-or-create is atomic, so concurrent identical calls cannot create two acceptances. The ledger email is sent at most once per acceptance.
- The assertion lifetime is 300 seconds.

**Retry**

- Safe to retry with the same inputs. Read `reuse` and `side_effects` rather than assuming a new acceptance.
- `ledger_email_failed`: the acceptance is recorded and the assertion exists; a retry re-sends only the ledger email.
- `internal_error` after signing: `side_effects.assertion_minted` is `true`; a retry re-mints against the existing acceptance.
- Never retry by changing `accepted_tos_text` or `accept_tos_hash` unless the terms changed. That would be a different acceptance.

**Errors**

| Code | Retryable | Meaning |
| :--- | :-: | :--- |
| `tos_text_hash_mismatch` | no | `accepted_tos_text` does not hash to `accept_tos_hash`. Re-read the terms and recompute. |
| `human_suspended` | no | The human account is suspended. |
| `human_email_unverified` | no | The human has not verified their email. |
| `master_tos_unsigned` | no | The human has not signed the Master Agent Delegation agreement. |
| `agent_revoked` | no | The agent is revoked (kill switch or abuse report). |
| `scope_not_granted` | no | The agent lacks `tos:accept` or one of `requested_scopes`. |
| `ledger_email_failed` | yes | Acceptance recorded, mail dispatch incomplete. |
| `internal_error` | yes | Broker, database or issuance failure. |

## identity_record_signup

Title: "Record signed-up service proof". Verifies the provider's signed `signup_token` and records the attribution proof for the authenticated human.

**Inputs**

| Field | Type | Required | Constraint and meaning |
| :--- | :--- | :-: | :--- |

### Behavior, side effects and retry

- Verifies the token signature, `typ`, `aud`, `iss`, the claims shape and the ownership against the trusted agent row before writing.
- Cross-checks the token's ToS URL and hash against the recorded acceptance. A token that references an acceptance the broker has not recorded fails with `signup_token_not_linked`.
- Validates `context.url` statically: absolute HTTPS (localhost development exception), `sha256:` digest format, and a host on the provider's registrable domain. The broker never fetches the guide, so this path is not an SSRF surface.
- Inserts or refreshes one `service_signups` proof row. Idempotent on `signup_token_jti`, on `assertion_jti`, and on `(agent, audience, provider_account_id)`.
- Sends no email and stores no provider credential.
- Retry: safe with the same token. A repeated token returns the existing proof; a fresh token for the same account refreshes the row.

**Errors**

| Code | Retryable | Meaning |
| :--- | :-: | :--- |
| `signup_token_invalid` | no | Signature, `typ`, audience or claim shape failed. Obtain a valid token. |
| `signup_token_not_linked` | no | The receipt references an acceptance this broker has not recorded for the audience. Call `identity_prove` first, then retry. |
| `signup_token_ownership_mismatch` | no | The receipt belongs to another human owner. Do not retry this token. |

## inbox_wait_for_email

Title: "Wait for a matching email". Waits for a matching inbound message and returns it with any detected OTP.

**Inputs**

| Field | Type | Required | Default | Constraint and meaning |
| :--- | :--- | :-: | :--- | :--- |
| `from_contains` | string | no | - | Case-insensitive substring of the sender address. |
| `subject_contains` | string | no | - | Case-insensitive substring of the subject. |
| `since_seconds_ago` | integer | no | `60` | Lookback window in seconds. Only messages received within it are considered. |
| `timeout_seconds` | integer | no | `30` | `minimum: 1`, `maximum: 60`. Wait budget. |

**Behavior**

- Checks the database immediately, so a message that already arrived is returned without waiting.
- Otherwise waits on a Realtime subscription plus a 1.5-second polling loop, and stops at the timeout.
- Only inbound messages for the active agent match; the newest match wins. No message is consumed.
- `detected_otp` uses the same extraction as `inbox_read`.
- Result keys: `id`, `agent_id`, `from_address`, `to_address`, `subject`, `text_body`, `html_body`, `received_at`, `detected_otp`.

**Retry**

- Safe. Use a longer `timeout_seconds`, a wider `since_seconds_ago`, or narrower filters.
- Do not poll in a tight loop. One wait with a 30-60 second budget is cheaper than repeated short calls.

**Errors**

| Code | Retryable | Meaning |
| :--- | :-: | :--- |
| `wait_timeout` | yes | Nothing matched within the wait budget. |
| `agent_revoked` | no | Agent revoked. |
| `scope_not_granted` | no | The agent lacks `inbox:read`. |
| `internal_error` | yes | Broker or database failure. |

**Example**

```json
{ "timeout_seconds": 1, "from_contains": "no-such-sender" }
```

Live on 2026-10-21:

## inbox_send

Title: "Send email from agent inbox". Sends mail from the agent's address and records it in the inbox ledger.

**Inputs**

| Field | Type | Required | Constraint and meaning |
| :--- | :--- | :-: | :--- |
| `to` | string | yes | `format: email`. One recipient. |
| `subject` | string | yes | `minLength: 1`. |
| `text` | string | yes | `minLength: 1`. Plain-text body. |
| `html` | string | no | Optional HTML alternative. `text` stays the plain-text part. |

No `cc`, `bcc`, attachments or reply headers in v1.

**Result**

| Key | Type | Meaning |
| :--- | :--- | :--- |
| `ok` | `true` | Send completed and was recorded. |
| `message_id` | string | Broker inbox row id. |
| `resend_email_id` | string | Mail provider id. |
| `from_address`, `to_address`, `subject` | string | As sent. |
| `received_at` | ISO 8601 string | Row timestamp. |

**Side effects and retry**

- Sends one email through the mail provider, then inserts one outbound `inbox_messages` row.
- Not idempotent. A retry sends a second email.
- If the send fails, nothing is sent and nothing is recorded: `send_failed`, retryable.
- If the email is sent but the ledger insert fails, `internal_error` reports `side_effects.email_sent: true` and `message_recorded: false`. Check `inbox_list` before resending, because a retry re-sends.

**Errors**

| Code | Retryable | Meaning |
| :--- | :-: | :--- |
| `send_failed` | yes | The provider rejected or did not accept the message; nothing was sent or recorded. |
| `scope_not_granted` | no | The agent lacks `inbox:send`. |
| `agent_revoked` | no | Agent revoked. |
| `internal_error` | yes | Broker or database failure; check `side_effects`. |

**Example**

```json
{
  "to": "human@example.com",
  "subject": "Signed up for Example RP",
  "text": "The account exists and the credential is stored."
}
```

```json

  "resend_email_id": "re_01jdocsverify",

  "to_address": "human@example.com",
  "subject": "Signed up for Example RP",
  "received_at": "2026-10-21T10:02:00.000Z"
}
```
