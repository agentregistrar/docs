One canonical definition per term. Other pages link here instead of redefining
the same word. Where a term maps to a wire field, the field name is in
backticks. For a plain-language overview of how the pieces fit together, see
[How it works](/start/how-it-works/).

## Roles and records

**Human owner.** The verified person accountable behind every agent. The human
verifies an email address, accepts the Master Agent Delegation Agreement, and
is attributed for what their agents sign up for. The broker identifies the human
with `human.id`, and assertions carry `human.verified` (which proves email
verification, never KYC). See [Trust and limits](/start/trust-and-limits/).

**Agent (agent sub-identity).** A broker identity record (`agt_...`) with a
display name, harness label, dedicated `<agent-slug>@<domain>` inbox address,
and delegated scopes. It is not a model or process; it is the delegated identity
bound to an OAuth 2.1 MCP connection when the human approves the client during
OAuth consent (either creating a new agent up to `max_active_agents`, default
`2`, or binding an existing active agent). See [Developer
Portal](/agents/portal/) and [Broker HTTP and OAuth](/reference/broker-http/#oauth-21-with-agent-binding).

**Harness (coding tool / MCP client).** The client that connects to the broker's
`/mcp` endpoint and runs the agent, such as Claude Code, Cursor, OpenCode,
Codex CLI, Gemini CLI, Antigravity CLI, VS Code, Claude Desktop, or a generic
OAuth-capable MCP client. The harness holds the OAuth 2.1 session and bearer
token bound to one active agent. See [Install MCP](/agents/install/).

**Broker.** The service that verifies humans, hosts agent inboxes, mints signed
assertions, records terms acceptances and signup receipts, and serves the MCP
endpoint. In these docs, the hosted broker is `https://agentregistrar.dev`
(**Agent Registrar**). The protocol keeps human-broker and provider-broker roles
separate so multiple brokers can interoperate. See [Broker HTTP and
OAuth](/reference/broker-http/).

**Provider (relying party / RP).** A software service that accepts brokered
agent signups by publishing a discovery document and verifying signed assertions
at its own signup endpoint. A provider keeps its own domain, accounts,
credentials, pricing, and UX. Publishing an optional verification credential
(`attestation`) lets default `verify` clients recognize the provider's verified
domain; a conformant provider without one is unverified, not invalid. See
[Providers](/providers/).

**Delegated scopes.** The permissions stored on an agent sub-identity and
embedded in assertions as `delegation.scopes`. Newly created agents start with
`tos:accept`, `signup:free_tier`, and `inbox:read`. See [Assertion
claims](/protocol/assertion-claims/#claim-set).

## Protocol artifacts

**Agent Identity Protocol.** The open Apache-2.0 agent-signup and Day-2
re-login contract. Its prose name is Agent Identity Protocol; its wire
identifier is `agent-identity-protocol`; its wire version is `2.0`
(`protocol_version: "2.0"`). The current specification release is `v2.3.0`. See
[Protocol](/protocol/).

**Protocol version.** The wire version carried in discovery `protocol_version`
(`"2.0"`), distinct from the specification document and package release tag
(`v2.3.0`).

**Discovery document.** The identity-only JSON served at
`GET /.well-known/agent-signup.json` on the provider's canonical origin:
protocol name and version, `audience`, `provider_name`, `issuer_allowlist`,
`required_scopes`, `terms` (`version`, `url`), optional `attestation`,
`endpoints.agent_signup`, and optional `endpoints.agent_login` (`v2.2.0` Day-2
re-authentication). It never carries catalogs, pricing, or provisioning
endpoints. See [Discovery fields](/protocol/discovery-fields/).

**Issuer allowlist.** The `issuer_allowlist` array in discovery naming exact
broker origins the provider accepts. The assertion's `iss` must match one entry
exactly or the provider rejects it with `issuer_not_allowed`. See [Discovery
fields](/protocol/discovery-fields/#required-fields).

**Required scopes.** The `required_scopes` array in discovery naming scopes the
provider requires at signup (always including `tos:accept`). Missing any entry
produces `insufficient_scope`. See [Discovery
fields](/protocol/discovery-fields/#required-fields).

**Terms.** The provider's agreement identified in discovery by `terms.url` and
`terms.version`. At signup, the broker fetches `terms.url` and computes a
SHA-256 hash over the exact UTF-8 response bytes, recording it in
`delegation.accepted_rp_tos_hash` and the Activity audit trail. See [terms
binding](/protocol/specification/#6-tos-binding).

**Master Agent Delegation Agreement (Master ToS).** The single agreement a human
owner accepts with the broker to authorize agents to accept provider terms on
their behalf. Its version and optional hash appear in assertions as
`delegation.master_tos_version` and `delegation.master_tos_hash`. See [Trust
and limits](/start/trust-and-limits/).

**Assertion (signed identity token).** A short-lived Ed25519-signed JWT
(`typ: agent-id+jwt`) proving the agent, verified human owner, purpose
(`"signup"` with 5-minute default TTL, or `"login"` with uncached 120-second TTL
and single-use `jti`), and accepted terms for one exact `aud`. Minted by
`identity_signup` or `identity_login` and sent verbatim inside `signup_request`
or `login_request`. See [Assertion claims](/protocol/assertion-claims/).

**JTI.** The unique identifier on a signed token: `jti_...` on an assertion,
`srp_...` on a signup receipt, or `abr_...` on an abuse report. A provider
resolves a repeated assertion `jti` for the same agent, account, and service
idempotently and returns `assertion_replayed` only on a conflicting context.

**Acceptance.** A durable delegated consent event recorded in the broker's
acceptance ledger (`tos_acceptances`) per agent, audience, and fetched terms
hash. Assertions are short-lived proofs referencing an acceptance; re-minting an
assertion does not create a new legal consent.

**Activity (audit trail).** The unified `/activity` view in the Developer Portal
joining every recorded terms acceptance (`tos_acceptances`) with its strongest
signup receipt (`service_signups`). Neither table is a resource or credential
inventory. See [Developer Portal](/agents/portal/).

**Email forwarding mode.** The Developer Portal `/settings` preference
controlling which inbound agent inbox messages forward to the human owner's
verified email: `all` (default), `legal_only`, or `off`. Terms acceptance
receipts are always emailed to the human owner regardless of forwarding mode.
See [Inbox and verification](/agents/inbox-and-verification/).

**Signup receipt (`signup_token`).** Optional provider-signed Contract E JWS
(`typ: agent-signup-receipt+jwt`, `srp_...`, no `exp`) proving that a signup
occurred, signed with a key listed in the provider's historical attestation.
Submitted asynchronously server-to-server via Contract F (discovered from
`signup_receipt_endpoint` in `/.well-known/agent-broker.json`, falling back to
`POST /api/broker/signup-receipt`) or by the agent via `identity_record_signup`.
Not a provider credential. See [Receipt and context](/protocol/receipt-and-context/).

**Context guide (context pointer).** Optional hash-pinned pointer
(`context.url` and `context.sha256`) returned at signup and inside a receipt,
linking to the provider's post-signup guide (commonly `SKILL.md`) on the signup
endpoint's registrable domain. The agent fetches the guide, verifies the
SHA-256 digest, and treats it as untrusted data. See [Receipt and
context](/protocol/receipt-and-context/#the-context-pointer).

**Resolution.** Optional signup response field: `"created"` when a new account
was created, or `"resolved"` when an existing account was matched idempotently.
`"resolved"` is a success and must not mint duplicate credentials or mail. See
[Receipt and context](/protocol/receipt-and-context/#the-signup-response).

**Provider credential.** The vendor secret (such as an API key) returned once by
the provider in the signup response. The broker never stores, proxies, or sees
provider credentials; the agent persists them immediately at handoff and uses
the provider's recovery path if one is lost. See [Credentials and
recovery](/agents/credentials-and-recovery/).

**Provider verification credential.** Optional broker-issued Contract G JWS
(`typ: agent-rp-attestation+jwt`, `alg: EdDSA`) binding a provider's canonical
origin, `audience`, identity, assurance level (`domain` or `entity`), and
optional `keys[]` (may be empty `[]` for keyless broker-managed verification).
Discovery publishes only the `attestation` source object (`mode: "broker" |
"provider"`, `uri`), never the raw token. Public prose uses this term so bare
"provider credential" keeps its signup-secret meaning. See [Discovery
fields](/protocol/discovery-fields/#the-optional-attestation-source).

**Verified provider / unverified provider.** Whether a provider's optional
verification credential verified under the human owner's trust policy at
`checked_at`. Verification checks domain control or reviewed legal-entity
evidence only; it is never a safety, endorsement, or uptime guarantee. A
conformant provider without `attestation` is unverified, not invalid. See
[Trust and limits](/start/trust-and-limits/).

**Trust list and verification policy.** Per-human settings in `/trust` combining
trusted RP-broker issuers with a verification policy mode: `verify` (default;
requires a valid credential in either publication mode), `no_verify` (allows
unverified providers), or `strict` (requires broker-managed credentials only).
Blocking a provider is a separate action checked before any mode. See [Trust
and limits](/start/trust-and-limits/).

**Conformance vs verification.** Conformance checks discovery document shape,
required fields, forbidden vendor fields, and `attestation` object host binding.
Verification fetches the advertised attestation source and validates its JWS
against trusted broker keys and policy. See [Conformance
validator](/protocol/validator/).

**Proof source.** Transport and strength authority recorded on a signup proof:
`rp_callback` (Tier 1, provider posted to Contract F), `rp_signed` (Tier 2,
agent submitted the provider-signed receipt via `identity_record_signup`), or
historical `agent_self_reported`. Only `rp_callback` and `rp_signed` with a
verified attestation give an abuse report standing. See [Receipt and
context](/protocol/receipt-and-context/#contract-f-and-proof-sources).

## MCP and transport

**Model Context Protocol (MCP).** The JSON-RPC 2.0 protocol served by the broker
at `https://agentregistrar.dev/mcp` (server name `agentregistrar`, version
`1.1.0`). See [MCP tools](/reference/mcp-tools/#endpoint-and-discovery).

**MCP tool.** One of the five callable broker operations in `tools/list`:
`identity_whoami`, `identity_signup`, `identity_login`,
`identity_record_signup`, and `inbox_read`. Tool errors return `isError: true`
with a structured JSON error envelope, not an HTTP error. See [MCP
tools](/reference/mcp-tools/).

**MCP resource.** One of the four static, read-only `text/markdown` documents
advertised under `agentregistrar://docs/*` (`quickstart`, `assertion-claims`,
`error-recovery`, `spec`). See [MCP resources](/reference/mcp-tools/#mcp-resources).

**MCP bearer token.** The opaque `mca_...` OAuth 2.1 access token (24-hour
lifetime, stored only as a SHA-256 hash) bound to one human owner and one active
agent sub-identity. Paired with an atomic rotating `mcr_...` refresh token. See
[Broker HTTP and OAuth](/reference/broker-http/#post-apioauthtoken).

**OAuth 2.1, DCR, and CIMD.** The authorization flow protecting `/mcp`:
authorization code with PKCE `S256`, RFC 7591 dynamic client registration
(`POST /api/oauth/register`), and Client ID Metadata Documents (`https://`
`client_id` URLs). See [Broker HTTP and
OAuth](/reference/broker-http/#oauth-21-with-agent-binding).

## Operations and controls

**Kill switch (revocation).** The per-agent revocation control in the Developer
Portal (`/agents/[id]`). Revoking an agent sets its status to `revoked`,
immediately stops new assertions and inbox access (`agent_revoked`), and rejects
OAuth refreshes for that agent without affecting other agents. Revocation does
not delete existing provider accounts, revoke provider API keys, or undo
recorded terms acceptances. See [Developer Portal](/agents/portal/).

**Operator suspension.** A protective broker-operator action setting an agent's
status to `suspended` (for example, following a verified receipt-linked abuse
report). Operator suspension blocks all tool calls (`agent_revoked`) and blocks
authorizing new OAuth connections (`403 access_denied`) until restored by a
broker operator; it cannot be cleared by the human kill switch or by creating a
new agent. See [Trust and limits](/start/trust-and-limits/).

**Abuse report.** A provider's authenticated report against an agent sent to
`POST /api/broker/report-abuse` as `{ rp_attestation, report }` (5-minute JWS).
A report linked to an RP-signed signup with a verified attestation is `verified`
and may trigger protective suspension pending operator review; an unlinked
report opens a case without suspending. See [Abuse
reporting](/providers/guides/abuse-reporting/).
