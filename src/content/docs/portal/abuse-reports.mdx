A relying party can report an agent through the broker's abuse endpoint. The report is a notification and revocation path, not a dispute process. This page describes what the broker actually does with a report and what the human should do next.

## How a provider reports abuse

The provider sends a JSON request to `POST /api/broker/report-abuse` on the broker origin:

```json
{
  "agent_id": "agt_...",
  "reporter_service": "provider.example",
  "reason": "what the agent did",
  "evidence_jti": "jti_..."
}
```

`agent_id`, `reporter_service` and `reason` are required. `evidence_jti` is optional and should carry the assertion or receipt identifier the provider is relying on.

A successful response returns:

```json
{
  "ok": true,
  "agent_id": "agt_...",
  "agent_status": "revoked",
  "human_notified": true
}
```

`human_notified` is best effort. A `false` value means the alert was not delivered; it does not mean the revocation failed.

## What the broker does

1. Validates the request and resolves the agent.
2. Stores the report as an abuse report row.
3. Revokes the agent immediately, with the reporter's reason as the revocation reason.
4. Looks up the human owner and attempts to send an alert to the verified email.
5. Returns the response above.

The revocation happens before the alert. A mail failure does not roll it back.

## What the human receives

When delivery succeeds, the verified human owner receives an alert with:

- The agent id and name.
- The reporting service.
- The reason.
- The evidence JTI, if one was supplied.
- A reply path for contacting the broker if the report is wrong.

The report also appears in the **Abuse reports** tab on the agent detail page.

## What the human can do

- Read the report and check the agent's ledger and inbox for the activity described.
- Contact the provider to resolve the account or resource.
- Rotate any provider credentials the agent held.
- Keep the agent revoked, or reactivate it only after investigating.
- Preserve the agent id, report timestamp, evidence JTI and related ledger rows.

## What the broker does not do

- It does not adjudicate the dispute or decide who is right.
- It does not delete provider data, close a provider account or issue a refund.
- It does not guarantee that the provider stops using data it already received.
- It does not guarantee delivery of the human alert.
- It does not provide a public abuse or security address on this docs site. Use the reply path in the alert rather than an address you cannot verify.

## Contact path

The current public docs do not publish a security or abuse email address. The reliable paths are:

- The provider reports through `POST /api/broker/report-abuse`.
- The human replies to the abuse alert sent to the verified email.
- A human who suspects account compromise follows [Kill switch and revocation](/portal/kill-switch-and-revocation/).

If you operate a provider and need the request and response contract, the endpoint behavior above is the current implementation. The assertion and receipt fields are defined under [Protocol](/protocol/); the broker's HTTP surface is summarized under [Reference](/reference/).
