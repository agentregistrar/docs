Every agent gets its own receive-only email address of the form `<agent-slug>@agents.agentregistrar.dev`. Providers send welcome emails, legal receipts, billing alerts, and email verification codes to that address. Your agent reads the inbox through one MCP tool (`inbox_read`), and you can view every message live in the Developer Portal or forward it to your verified email.

## How the agent address works

- The address is generated when you create the agent during browser OAuth consent, combining a slug of your chosen name with a short unique suffix so duplicate names never collide.
- It stays fixed for the life of the agent (renaming an agent in `/agents/[id]` changes its display label only, never its email address).
- The inbox is **receive-only** over MCP: agents can read incoming mail when they hold the `inbox:read` scope, and cannot send outbound email.
- Treat it as a monitored channel, not a throwaway inbox: services may deliver account notices and legal updates there.

## Reading mail with `inbox_read`

One tool handles all three inbox workflows: listing recent messages, reading a full message by ID, and waiting for a new inbound email to arrive.

| Parameter | Type | Range / Default | Used in |
| :--- | :--- | :--- | :--- |
| `message_id` | UUID string | optional | Read one full message (returns `text_body`, `html_body`, `headers`, `detected_otp`) |
| `wait_seconds` | integer | `1` to `25` | Poll for a matching recent inbound email (every 1.5s up to 25s) |
| `since_seconds_ago` | integer | `1` to `3600` (default `120`) | Lookback window when `wait_seconds` is set |
| `from_contains` | string | optional | Case-insensitive substring match against raw `from_address` |
| `subject_contains` | string | optional | Case-insensitive substring match against `subject` |
| `limit` | integer | `1` to `20` (default `5`) | Max messages returned in list mode |

### Mode 1: list recent messages

Call `inbox_read` without `message_id` or `wait_seconds` to inspect the newest messages (up to 20, default 5). Each item includes `id`, `from_address`, `subject`, `received_at`, `is_legal_or_tos`, `detected_otp`, and a truncated `text_body` (up to 2,000 characters):

```json
{
  "name": "inbox_read",
  "arguments": {
    "limit": 5,
    "subject_contains": "VaporCloud"
  }
}
```

### Mode 2: wait for a verification email

When a provider sends an asynchronous welcome or verification email right after signup, pass `wait_seconds` (up to `25`) and narrow the match with `subject_contains` or `from_contains`:

```json
{
  "name": "inbox_read",
  "arguments": {
    "subject_contains": "Verification",
    "wait_seconds": 20,
    "since_seconds_ago": 300
  }
}
```

If a matching inbound email arrived within `since_seconds_ago` (default `120` seconds) or arrives before `wait_seconds` elapses, `inbox_read` returns it immediately. Otherwise it returns `wait_timeout` with `retryable: true` and no side effects.

Two common filter pitfalls:

- **Lookback window:** if the email arrived more than two minutes ago, raise `since_seconds_ago` (up to `3600`) or omit `wait_seconds` to list recent messages instead.
- **Substring matching:** `from_contains` matches the raw sender address (for example `noreply@agents.agentregistrar.dev`), not the provider's website domain if the sender uses a different mail domain.

### Mode 3: read one full message

Pass a `message_id` from list mode to fetch the complete `text_body`, `html_body`, `headers`, and `detected_otp`:

```json
{
  "name": "inbox_read",
  "arguments": {
    "message_id": "5c1f0000-0000-4000-8000-000000000000"
  }
}
```

Asking for an ID that belongs to another agent or does not exist returns `message_not_found`.

## Automatic six-digit OTP extraction (`detected_otp`)

Every message returned by `inbox_read` includes a `detected_otp` field. Agent Registrar strips HTML tags first (so codes split across tags are not accidentally glued together) and extracts the first standalone six-digit number found across the subject, plain-text body, and HTML body. If no standalone six-digit code is present, `detected_otp` is `null`.

Example response shape for a verification email:

```json
{
  "id": "5c1f0000-0000-4000-8000-000000000000",
  "direction": "inbound",
  "from_address": "Example Service <noreply@example.com>",
  "to_address": "claude-code-macbook-1a2b3c@agents.agentregistrar.dev",
  "subject": "Your verification code: 482910",
  "text_body": "Your verification code is 482910.",
  "html_body": "<p>Your verification code is <strong>482910</strong>.</p>",
  "headers": {},
  "is_legal_or_tos": false,
  "received_at": "2026-11-22T10:03:02.000Z",
  "detected_otp": "482910"
}
```

`detected_otp` is a convenience helper for provider-specific email verification flows. Submit the code only to the provider's own verification endpoint and never treat it as an Agent Registrar token.

## Email forwarding modes (`/settings`)

Every inbound email to your agents is stored and viewable in the Developer Portal (`/agents/[id]` -> **Live Inbox**). In [agentregistrar.dev/settings](https://agentregistrar.dev/settings), you choose which inbound emails are also forwarded to your verified human email address:

| Mode | What forwards to your verified email |
| :--- | :--- |
| **`all`** (default) | Every inbound email delivered to any of your agents |
| **`legal_only`** | Only inbound notices matching terms, legal, billing, invoice, privacy, security, or abuse keywords |
| **`off`** | No inbound agent emails are forwarded; view them in the portal **Live Inbox** tab |

<Aside type="note" title="Terms acceptance copies always email to you">
Changing your forwarding mode to `legal_only` or `off` affects inbound provider mail only. Broker-generated copies of terms your agents accept via `identity_signup` are always emailed to your verified address regardless of your forwarding mode.
</Aside>

## Portal Live Inbox and privacy

You can inspect any agent's inbox directly in `/agents/[id]` under the **Live Inbox** tab, which updates live and displays plain text, rendered HTML, raw headers, and `is_legal_or_tos` badges.

- **Not private to the agent:** the human owner can read every message in the portal, and messages are persisted in the broker's inbox store.
- **Keep secrets out of email:** never ask a provider or agent to send long-lived API keys, passwords, or sensitive personal data through the inbox.
- **No duplicate welcome mail on retries:** repeating an identical `identity_signup` call while a token is unexpired sends no new terms copy, and conformant providers suppress duplicate welcome emails on `resolution: "resolved"`.
