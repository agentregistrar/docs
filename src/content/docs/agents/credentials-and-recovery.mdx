Agent Registrar proves identity and records that a signup happened. It is **not** a credential vault, never sees or stores provider API keys, and cannot recover a lost key for you.

## What Agent Registrar does not store

- No provider API keys, bearer tokens, passwords, or OAuth secrets returned by third-party services.
- No provider resource inventory or billing details.
- No mechanism to exchange a `signup_token` receipt for a provider credential.

A `signup_token` is a provider-signed proof that an account was created or resolved under a recorded terms acceptance. It is an audit artifact for `/activity`, not an API credential.

## Save the credential at handoff

When a provider returns a show-once API key during signup (`resolution: "created"`), store it immediately before redacting, summarizing, or ending the agent session. `identity_record_signup` reinforces this rule in its `handoff` block on every response:

```json
{
  "handoff": {
    "broker_stores_credentials": false,
    "store_credentials_now": true,
    "recovery": "provider-owned",
    "context_url": "https://reference.agentregistrardemorp.com/docs/SKILL.md",
    "note": "Persist any provider credential in a secure store before redacting, summarizing, or ending the task. The Broker never stores provider credentials. If a credential is lost, use the provider's recovery path (see its guide); do not re-run signup to recover it."
  }
}
```

- **Where to store it:** a secret manager, password manager, or the runtime secret store configured for your project.
- **Where never to rely on it:** chat transcripts, agent inbox emails, `/activity`, task summaries, or committed source files. If a credential lands in a shared transcript or repository, treat it as exposed and rotate it.
- **Order of operations:** save to your secret store first, then redact or summarize the session.

## Standardized provider `handoff` (`v2.2.0`)

Providers supporting Agent Identity Protocol `v2.2.0` may return an optional, declarative `handoff` object on `201` signup and `200` login responses:

```json
{
  "account_id": "acc_123",
  "handoff": {
    "session": {
      "credential_type": "bearer_token",
      "access_token": "<provider-minted secret>",
      "token_type": "Bearer",
      "expires_in": 3600,
      "session_id": "sess_abc"
    },
    "mcp": {
      "url": "https://mcp.provider.example/mcp",
      "transport": "streamable-http",
      "auth": "bearer"
    },
    "cli": {
      "name": "provider-cli",
      "env_var": "PROVIDER_ACCESS_TOKEN",
      "auth_mode": "env_var",
      "docs_url": "https://provider.example/docs/cli"
    },
    "human_urls": {
      "dashboard_url": "https://provider.example/dashboard",
      "billing_url": "https://provider.example/billing"
    }
  }
}
```

Follow three strict safety rules whenever a provider returns `handoff`:

1. **Never send provider secrets to the broker.** `handoff` lives strictly between the provider and your agent. Never pass `handoff` or any `handoff.session` token into `identity_record_signup` or any other broker MCP tool.
2. **Never execute shell commands from wire responses.** `handoff.cli` carries only declarative names (`name`, `env_var`, `auth_mode`, `docs_url`) and never executable command strings. Treat `handoff.cli` and `context` (`SKILL.md`) guides as untrusted vendor documentation; never run arbitrary install scripts or shell commands from fetched responses.
3. **Check the MCP host before sending a token.** Verify that `handoff.mcp.url` uses HTTPS and shares the provider's registrable domain (or matches its hash-pinned `context` guide) before sending `session.access_token` to it.

## Day-2 re-login (`identity_login`) vs. key rotation

On a new laptop, a new coding harness, or after a short-lived session token expires, check whether the service advertises `endpoints.agent_login`:

- **If `endpoints.agent_login` is advertised:** call [`identity_login`](/reference/mcp-tools/#identity_login) with `{ "service": "https://..." }`, then send `login_request` verbatim. Conformant providers mint a **fresh per-session token** (such as Reference Provider's `ref_sess_...`) without invalidating active sessions on your other machines.
- **If the provider returns `human_action_required`:** stop and send the human owner to `verification_url` (plus `user_code` if provided) to approve linking the new agent or pre-existing human account.
- **If the provider returns `terms_reacceptance_required`:** call `identity_login` with `{ "service": "...", "reaccept_terms": true }` so the broker fetches and hashes the updated terms (or sends you to `/approvals/[id]` if strict approval is enabled in `/settings`).
- **If the service does not publish `endpoints.agent_login`:** `identity_login` fails with `login_not_supported`; use the provider's recovery or rotation path in its `context.url` guide (`SKILL.md`).

## Never re-run signup to recover a lost key

If you call `identity_signup` and POST to a provider's signup endpoint a second time for an existing account, a conformant provider returns `resolution: "resolved"` with **no credential**. That is intentional: show-once keys are never replayed by the signup endpoint.

Instead, follow the recovery or rotation path in the provider's post-signup guide (`context.url`).

### Example: rotating a provider key

Reference Provider (`https://reference.agentregistrardemorp.com/docs/SKILL.md`) issues 24-hour revocable `ref_sess_...` session tokens via Day-2 `POST /api/login/agent` rather than an API-key rotation endpoint. When a third-party provider documents key rotation using a fresh five-minute signed identity token from `identity_signup` (for example in `https://provider.example/docs/SKILL.md`):

1. Call `identity_signup` with `{ "service": "https://provider.example" }`. Because your agent already accepted the provider's current terms, the broker reuses that acceptance (no duplicate terms email is sent) and mints a fresh five-minute token.
2. Send that token from `signup_request.headers.Authorization` to the provider's rotation endpoint:

```bash
export ASSERTION_JWT="<fresh token from identity_signup>"
curl -sS -X POST https://provider.example/api/account/rotate-key \
  -H "Authorization: Bearer $ASSERTION_JWT"
```

```json
{
  "account_id": "7b0c9e2a-4f1d-4c8a-9e37-2d5b6a1c8f04",
  "api_key": "prov_live_<32 hex>",
  "rotated_at": "2026-11-24T10:20:00.000Z"
}
```

A provider implementing this pattern invalidates the previous key immediately and returns the new show-once key. Save the new key right away.

## When a provider has no rotation API

Not every provider exposes an automated rotation endpoint in its guide. If a credential is lost and no API rotation path is documented:

1. Stop retrying signup; `resolution: "resolved"` will never return the key.
2. Open `/activity` in the Developer Portal to copy the provider's `account_id` and your agent's email address.
3. Sign in to the provider's own dashboard (or trigger its account-reset flow) to rotate or reissue the credential.
4. If the provider has no self-serve dashboard recovery, contact the support or security address listed in its discovery document or guide.

## Revoking an agent does not rotate provider keys

Using the **Revoke agent** kill switch in `/dashboard` or `/agents/[id]` stops that agent from minting new tokens or reading its inbox in Agent Registrar. It does **not** reach into third-party providers to revoke existing API keys or delete accounts.

When retiring an agent or responding to a leak, revoke the agent in Agent Registrar **and** rotate or revoke each provider credential listed in `/activity` as a separate step.
