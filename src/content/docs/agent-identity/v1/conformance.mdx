A relying party is `agent-identity-v1` conformant when the discovery document it
serves at `GET /.well-known/agent-signup.json` passes the conformance validator
with zero errors. Conformance is about the discovery document, not the vendor's
product.

**Conformance is not verification.** A malformed `attestation` object, an
invalid `uri`, a URI on the wrong host, or a document that still embeds
`rp_attestation` is a conformance error. An expired, invalid, untrusted, or
unavailable source is a separate verification result. Conformance never calls
Broker B; only explicit attestation verification fetches the source.

The normative checklist is [spec section
21](/agent-identity/v1/specification/#21-conformance-checklist--minimal-conformant-example).
The validator reference is the generated [Conformance
validator](/agent-identity/v1/validator/) page.

## Relying-party checklist

- [ ] `GET /.well-known/agent-signup.json` returns `200` with `Content-Type: application/json`.
- [ ] `GET` returns `404` or `410`, never `401` or `403`, when the service does not support the protocol.
- [ ] `protocol` is exactly `agent-identity-v1`.
- [ ] `audience`, `provider_name`, a non-empty `issuer_allowlist`, and unique `required_scopes` including `tos:accept` are present.
- [ ] `terms.text` is the complete ToS text; `terms.sha256` is `sha256:` plus 64 lowercase hex characters over its exact UTF-8 bytes; `terms.url` and `terms.version` are present and consistent.
- [ ] `endpoints.agent_signup` is the only endpoint and is an absolute URL.
- [ ] `attestation` is omitted, or is an object with `mode` exactly `broker` or `provider` and a stable absolute HTTPS `uri` with no credentials and no fragment. Omission means **unverified**, not invalid. A `broker` URI is on an `issuer_allowlist` origin; a `provider` URI is on the discovery origin or a subdomain.
- [ ] `rp_attestation` does not appear anywhere in discovery. Its presence is `rp_attestation_removed`.
- [ ] No forbidden vendor field appears anywhere, including under `extensions`.
- [ ] CORS and cache headers follow [spec section 4](/agent-identity/v1/specification/#4-discovery-endpoint--transport); the body is within the 1 MiB cap.
- [ ] Assertions are verified against issuer JWKS with every check in [spec section 7.1](/agent-identity/v1/specification/#71-handshake).
- [ ] Stable [section 7.2](/agent-identity/v1/specification/#72-error-envelope-and-stable-codes) error codes are returned.
- [ ] If a `context` pointer is used, it is on the vendor's registrable domain, uses HTTPS, and is hash-pinned. It is returned in the signup response and receipt, not in discovery.
- [ ] A `signup_token` is RP-signed, names `service.origin`, `service.attestation_jti`, and `service.key_id`, has no `exp`, and carries no `instance_sku` or `endpoint_url`.
- [ ] If the provider claims verification, it publishes a valid credential and the registry entry carries all five `verification` fields from a live check.
- [ ] A repeated signup for an existing account, keyed as recommended in [spec section 9.1](/agent-identity/v1/specification/#91-account-identity-keys), resolves idempotently: it returns `resolution: "resolved"`, does not re-issue provider credentials and sends no duplicate welcome or legal mail. This is a `SHOULD`.
- [ ] The vendor guide documents a credential recovery or rotation path reached after signup, and that path is not advertised in discovery or the receipt. This is a `SHOULD`.

## Two independent results

| Result | What it covers | What it does not do |
| :--- | :--- | :--- |
| **Document conformance** | Schema, ToS hash, scope boundary, field rules, the `attestation` object, and the removed `rp_attestation` carrier. | It never requires Broker B to be up or fetches the source. |
| **Attestation verification** | Optional source fetch, JWS parse, trusted issuer before fetch, signature, `typ`/`alg`/`kid`, time, origin/audience binding. | It does not make the provider safe or change the conformance verdict. |

A malformed `attestation` object (not an object, a `mode` other than
`broker`/`provider`, a non-string `uri`), a relative/non-HTTPS/credentialed/
fragment-bearing `uri`, or a failed mode host binding makes the run exit `1` and
reports `attestation.status: "not_checked"`, never `invalid`. An absent object is
`unverified` and does not fail the run. A typed broker answer (`403`, `404`,
`410`, `429`, `5xx`) is a verification result, not a conformance failure: `403`
is `suspended`, `404` is `unverified`, `410` is `invalid` with reason
`attestation_revoked`, and `429`/`5xx` are `unavailable`.

A file-mode run with no fetch origin cannot check a `provider` URI's binding; it
reports the binding as unchecked and the result as `unavailable` with reason
`origin_unverifiable`. A `broker` URI binding is still checked from the
document's `issuer_allowlist`.

## Validate a document

Run the validator from a clone of `agentregistrar/spec` at the pinned tag. The
package is source-first; install its dependencies first.

```bash
pnpm install
pnpm validate:discovery fixtures/valid-minimal.json
pnpm validate:discovery https://example.com/.well-known/agent-signup.json
```

For machine-readable output, pass `--silent` so stdout is pure JSON:

```bash
pnpm --silent validate:discovery https://example.com/.well-known/agent-signup.json --json | jq .
```

Verify the optional credential:

```bash
pnpm validate:discovery https://example.com/.well-known/agent-signup.json \
  --verify-attestation \
  --trusted-rp-broker https://agentregistrar.dev
```

Turn it into a gate with `--require-attestation`. Use `--jwks` to pin one
issuer's JWKS for an offline run and `--at` to freeze the clock for fixtures.

Opt-in probes are non-destructive and off by default:

```bash
pnpm validate:discovery https://example.com/.well-known/agent-signup.json --probe-jwks
pnpm validate:discovery https://example.com/.well-known/agent-signup.json --probe-endpoints
```

Probes never `POST`, never trigger signup or provisioning, and are limited to the
issuers in `issuer_allowlist` and the advertised `endpoints.agent_signup`.

## Exit codes

| Code | Meaning |
| :--- | :--- |
| `0` | Valid conformant document, and no required verification failed. Warnings are allowed and do not change the code. |
| `1` | A document was obtained and parsed, but it failed conformance (including a malformed `attestation` object, a failed host binding, a present `rp_attestation`, or unparseable JSON), or a required attestation check failed. |
| `2` | Could not obtain what was needed: unreadable file, network or timeout failure, redirect limit or cross-origin redirect, non-`200` status, wrong content type, over the size cap, or the attestation source or JWKS unavailable under `--require-attestation`. The conformance verdict is not evaluated. |

Exit `2` is "no usable run" and exit `1` is "bad document or failed gate". Both
are non-zero, so a gate that checks only the exit status still fails correctly.

## Fixtures

The spec repository ships conformance and attestation fixtures:

- `fixtures/valid-*` documents pass with exit `0`.
- `fixtures/invalid-*` documents fail with exit `1` and a field-level message.
- Attestation fixtures cover broker-managed, provider-managed, absent, invalid
  mode, relative/HTTP/userinfo/fragment URI, broker or provider wrong host, the
  removed `rp_attestation` field, typed `403`/`404`/`410`/`503`, and an expired
  source.
- `--source-response <path>` injects a `{status, body, contentType}` response for
  offline source verification. It performs no network I/O and never echoes the
  body.
- A fixture's `__fixture_note` field is an unknown top-level field and produces a
  warning only. `__fixture_origin` declares the fetch origin for offline binding.

Run `pnpm validate:fixtures` for the full matrix. See the generated
[Conformance validator](/agent-identity/v1/validator/) page for the `--json`
field reference.

## Registry entry

A validator-passing discovery document is the objective entry criterion. The
registry is adoption infrastructure, not an enforcement mechanism.

Entry criteria:

1. The identity-only validator passes: `valid: true` with `exitCode: 0`.
   Warnings are permitted; errors are not.
2. The discovery document is public and stable: an HTTPS
   `/.well-known/agent-signup.json` on the implementation's canonical origin,
   not a throwaway or per-deploy URL.
3. The contact is reachable: a security, abuse or legal contact that someone
   monitors.
4. A post-signup context guide is published if the vendor has capabilities to
   document.
5. Optionally, a five-field `verification` snapshot if the entry claims
   verification.

Submission path: open a pull request against
[`agentregistrar/spec`](https://github.com/agentregistrar/spec) that adds one
object to the `implementations` array in
[`registry/implementations.json`](https://github.com/agentregistrar/spec/blob/main/registry/implementations.json)
and updates the table in
[`registry/README.md`](https://github.com/agentregistrar/spec/blob/main/registry/README.md).
Include `name`, `url`, `discovery_url`, `audience`, `protocol`, `capabilities`
(protocol capabilities only), `contact`, `validated_at`, `validator_version`,
and the exact command and counts in `validator_evidence`. If claiming
verification, include `broker`, `level`, `attestation_jti`, `checked_at`, and
`status`.

Registry capabilities are protocol capabilities only: `agent_signup` and
`post_signup_context`. Vendor features such as provisioning, catalogs, SKUs,
pricing and OTP endpoints are never registry capabilities.

**Conformance is not verification.** An entry with no `verification` object is
conformant and unverified. Only `verification.status: "active"` at `checked_at`
renders the verified badge; the conformance badge is separate, and neither is an
endorsement. The registry is a snapshot, not a live status feed.

## Known limits

- The registry lists discovery documents that pass the validator. It is not a
  broker endorsement of the implementation's product, security posture, uptime
  or pricing.
- A document can be conformant and still be a poor or malicious service.
  Conformance is a schema and scope check, not a trust decision.
- Verification is identity, not safety. A valid credential says a broker checked
  an origin and, at entity level, legal-entity evidence; it does not rate
  conduct.
- Warnings do not fail conformance. Review them, but do not treat a warning-free
  run as a security review.
