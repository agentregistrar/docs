VaporCloud is the reference relying party at [skdl.dev](https://skdl.dev). It sells fictional appliances, which is exactly why it is useful: the vendor surface is obviously vendor scope, and the identity-only protocol is easy to see.

This walkthrough separates what the protocol defines from what VaporCloud does as a product. The demo is not a production SLA and not a hosted service.

```json
  },

  },
  "extensions": {
    "dev.vaporcloud": {
      "support_url": "https://skdl.dev/support"
    }
  }
}
```

What to notice:

- One audience, one issuer allowlist and one endpoint. The broker origin is `https://agentregistrar.dev`.
- `required_scopes` includes `tos:accept`; the extra `signup:free_tier` is a VaporCloud scope, still a delegation requirement, not a catalog.
- `terms.sha256` is a real digest of the text. Recompute it and it matches.
- `extensions` carries a support URL under a reverse-DNS key. There is no catalog, no SKU, no provisioning endpoint and no OTP endpoint anywhere in the document.

The transport checks also passed: `200`, `application/json`, a 60-second cache and permissive CORS.

## The signup response (documented, not observed)

A live signup requires a real agent assertion from the broker, so this walkthrough did not create an account. The shape below is what the live VaporCloud guide documents, plus the `attribution` block the checked-in reference handler adds; it was not observed against the live service on 2026-10-21.

```json
{
  "account_id": "<opaque vendor account reference>",
  "resolution": "created",
  "vapor_api_key": "vc_live_<32 lowercase hex>",
  "signup_token": "<signed Contract E receipt>",
  "signup_token_jti": "srp_<...>",
  "context": {
    "url": "https://skdl.dev/docs/SKILL.md",
    "sha256": "sha256:<64 hex>"
  },
  "credential_recovery": {
    "available": true,
    "method": "rotate",
    "endpoint": "https://skdl.dev/api/account/rotate-key",
    "guide_url": "https://skdl.dev/docs/SKILL.md"
  },
  "attribution": {
    "agent_id": "agt_<...>",
    "agent_email": "<agent-slug>@agents.example",
    "human_owner": "<name> (<email>)",
    "human_email": "<email>",
    "accepted_tos_hash": "sha256:<64 hex>"
  }
}
```

Protocol fields and vendor fields are mixed in the HTTP response on purpose: `resolution`, `account_id` and `context` are protocol-adjacent; `vapor_api_key`, `credential_recovery` and `attribution` are vendor capability. The signed receipt carries only the identity facts, the opaque account id and the context pointer. It does not carry the key.

`vapor_api_key` is present only when `resolution` is `"created"`. On `"resolved"` the field is absent, `credential_recovery` points at the vendor's rotation endpoint, and `attribution` is refreshed. A repeated signup resolves the account; it does not reissue the key.

The guide is 10792 bytes and is versioned in its own text. The authoritative comparison value is the `context.sha256` in the signup response or receipt; the digest above records the bytes served on that date.

The guide documents the vendor API, including one provisioning call. Calling it without a credential shows the vendor error path:

```bash
curl -sS -X POST https://skdl.dev/api/provision \
  -H 'Content-Type: application/json' \
  -d '{"sku":"quantum-toaster-x1","name":"example"}'
```

Recorded output:

```text
{"error":"unauthorized","error_description":"Invalid VaporCloud API key or Agent Identity JWT"}
```

That error is VaporCloud's, not a protocol code. Provisioning is the vendor's API, called after signup and after the guide hash matches. The protocol ends before it.

## The administration view

`/admin` is a vendor page. It returns `200` HTML and is not part of discovery or the receipt. In the implementation it joins each provisioned resource to the agent id, agent email, human attribution and the accepted terms chain, and it can file a Contract D.2 abuse report.

What it demonstrates:

- an account can be traced to an agent and a human;
- the terms version and hash recorded at signup are visible;
- a vendor can act on abuse through the broker.

What it does not prove:

- that the human read the terms;
- that the agent is trustworthy;
- that the broker endorses the vendor or its product.

The admin view is vendor tooling. It is not a protocol requirement, and a provider can implement attribution however it likes.

## Vendor boundary

| Protocol | Vendor |
| :--- | :--- |
| Discovery fields, terms hash, issuer allowlist | Catalog, SKUs, prices and quotas |
| Assertion verification and stable errors | Provisioning and resource lifecycle |
| Optional receipt with identity facts | Credential format, rotation and recovery |
| Optional context pointer and digest | The guide's content, version and freshness |

VaporCloud keeps the vendor surface in `/docs/SKILL.md`, including its vendor error catalog. None of it appears in discovery or the receipt. That is the pattern to copy; the appliances are optional.

## Caveats

- `skdl.dev` is a demo, not a production service. It has no SLA.
- The registry entry is the reference implementation, but its recorded validation used the locally started implementation and its `.example` discovery URL. The live document above was validated separately on 2026-10-21. The exception is documented in the registry and is not a precedent.
- The live terms text contains characters that are not ASCII. Hash the bytes you serve; do not normalize them.
- A green validator result says the document conforms. It says nothing about the product.
