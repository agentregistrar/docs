Use the pre-launch checklist before taking live traffic and after changing keys, terms, or signup logic. If a check or live request fails, jump to the troubleshooting tables below.

## Pre-launch production checklist

### Transport and discovery

- [ ] `GET /.well-known/agent-signup.json` runs on canonical HTTPS (`localhost` is development only) and returns `200`, `application/json`, no auth, and no redirect.
- [ ] `Cache-Control` is `public, max-age=60` (at most 300) and `Access-Control-Allow-Origin: *` is set where needed.
- [ ] Discovery body is under 1 MiB, contains no forbidden capability fields at any depth, and is exempt from CDN bot challenges.
- [ ] Unsupported deployments return `404` or `410` rather than `401` or `403`.
- [ ] `issuer_allowlist` contains exact broker origins with no path, query, or wildcard.
- [ ] `npx @agentregistrar/discovery@2.1.1 validate https://<origin>/.well-known/agent-signup.json --json` exits `0` in CI or release checks.

### Terms lifecycle

- [ ] `terms` is `{ "version", "url" }` only (no `text` or `sha256`).
- [ ] `terms.url` serves deterministic UTF-8 bytes with no redirect and no per-request nonce or wrapper.
- [ ] Material terms edits ship new bytes and a new `terms.version` atomically.
- [ ] Stale `delegation.accepted_rp_tos_url` (or hash when checked) returns `409 tos_hash_mismatch`.

### Assertion verification and replay

- [ ] Signature verifies `alg: "EdDSA"`, `typ: "agent-id+jwt"`, and `kid` against `<iss>/.well-known/jwks.json`; `jku` and `x5u` headers are rejected.
- [ ] `iss`, `aud`, `exp` (at most 60s skew), `iat` (no more than 60s in the future), lifetime (`0 < exp - iat <= 300`), `delegation.scopes`, and `human.verified === true` are enforced strictly from the verified JWT payload.
- [ ] Account uniqueness `(iss, human.id)` (or `(iss, agent.id)`) and `jti` replay protection are backed by durable database constraints.
- [ ] `resolution: "resolved"` returns `200` with no credential and sends no duplicate welcome or legal emails.
- [ ] `POST` signup responses send `Cache-Control: no-store` and enforce rate limits (`429 rate_limited`).

### Attestation and optional keys

- [ ] Domain is verified in the [Provider Portal](/providers/portal/) (or you intentionally run unverified for `no_verify` clients only).
- [ ] Default broker-managed attestation needs no signing key (`keys: []`) and no renewal cron job.
- [ ] If opted into provider-managed attestation, renewal runs on a 12-hour target against the 24-hour TTL via `POST /api/provider/v1/attestation`, and never serves an empty file.
- [ ] Any optional RP Ed25519 private key (for receipts or Contract D.2 abuse reports) lives in a secret store, never in git or logs.
- [ ] If issuing receipts, the exact historical attestation naming `service.attestation_jti` is retained for Contract F delivery.

### Optional receipts, context guide, and incidents

- [ ] Receipt header is `alg: "EdDSA"`, `typ: "agent-signup-receipt+jwt"`, `kid === service.key_id`, with no `exp`, `tos.sha256 === delegation.accepted_rp_tos_hash`, and `iat`/`signed_up_at` inside the attestation window.
- [ ] `context.url` shares the signup endpoint's registrable domain, contains no secrets, and deploys atomically with `context.sha256`.
- [ ] Audit logs record `jti`, `iss`, `agent.id`, `human.id`, opaque `account_id`, terms version/URL/hash, and `created`/`resolved`, without logging credentials.
- [ ] `contact` in discovery reaches a monitored human inbox, and incident runbooks cover disabling signup, rotating keys, and sending Contract D.2 reports.

## Troubleshooting

### Discovery and validation

| Symptom | Cause | Fix |
| :--- | :--- | :--- |
| Validator fails a forbidden field | Catalog, SKU, provisioning, or OTP field in discovery or `extensions` | Remove capability fields and move them to your [context guide](/providers/guides/issue-signup-receipt/#post-signup-context-guide). |
| Validator exits `2` | DNS, TLS, redirect, non-`200`, wrong content type, oversize body, or source/JWKS unavailable under `--require-attestation` | Inspect headers with `curl -sS -D -` and fix transport before editing JSON. |
| `protocol` or `protocol_version` rejected | Legacy `agent-identity-v1` or missing `protocol_version` | Set `protocol: "agent-identity-protocol"` and `protocol_version: "2.0"`. |
| `field.rp_attestation` / `rp_attestation_removed` | Document still embeds legacy `rp_attestation` JWS | Remove `rp_attestation` and publish `attestation: { mode, uri }`. |
| `attestation_uri_host_untrusted` | `broker` URI origin is not in `issuer_allowlist` or trusted-broker list | Use the broker origin already listed in `issuer_allowlist`. |
| `attestation_uri_host_unbound` | `provider` URI points to a third-party host or external CDN | Host the provider-managed JSON on your discovery origin or a subdomain. |
| `terms.url` digest changes between fetches | Per-request nonce, timestamp, bot challenge, or dynamic banner | Serve deterministic UTF-8 bytes with no redirects. See [Publish discovery](/providers/guides/publish-discovery/). |

### Attestation status

| Symptom | Cause | Fix |
| :--- | :--- | :--- |
| `attestation.status: "unverified"` | No `attestation` object in discovery, or broker returned `404` | Verify your domain in the [Provider Portal](/providers/portal/) and publish the generated `attestation` block, or accept that `verify`/`strict` clients will refuse signups. |
| `attestation.status: "expired"` | Token is past `exp` | For broker-managed, verify `attestation.uri` and network reachability; for provider-managed, renew via `POST /api/provider/v1/attestation` before the 24-hour TTL. |
| `attestation.status: "suspended"` or `403 provider_suspended` | Provider or origin is suspended by the broker | Contact the broker operator; do not expect retries to clear suspension. |
| `attestation.status: "invalid"` with `attestation_revoked` | Broker answered `410` | Revocation is terminal for that attestation; check status with the broker operator. |
| `attestation.status: "unavailable"` | Network timeout, `429`, or `5xx` | Retry later; do not treat unavailability as `unverified`. |
| `strict` client rejects a valid token | Service uses `mode: "provider"` | Switch to broker-managed attestation (`mode: "broker"`). |

### Signature, JWKS, terms, and replay

| Symptom | Cause | Fix |
| :--- | :--- | :--- |
| `401 invalid_assertion` on every call | Wrong JWKS URL, local test override left in prod, wrong `alg`/`typ`, or proxy modifying header | Fetch `<iss>/.well-known/jwks.json`, remove `JWKS_URL_OVERRIDE` overrides, and require `EdDSA` plus `typ: "agent-id+jwt"`. |
| `401 invalid_assertion` after broker key rotation | JWKS cached without refresh | Refresh JWKS once on unknown `kid`; never hard-code `broker-key-1`. |
| `401 assertion_expired` immediately | Server clock skew over 60 seconds | Sync host clocks with NTP and allow up to 60 seconds of skew. |
| `403 issuer_not_allowed` or `audience_mismatch` | Trailing slash, path, or mismatched `audience` string | Match exact origin in `issuer_allowlist` and exact `audience` string. |
| `409 tos_hash_mismatch` | Terms changed without updating `terms.version`, or assertion carries stale terms URL/hash | Publish new bytes and `terms.version` atomically so agents re-discover and re-accept. |
| `409 assertion_replayed` on retry | Handler rejects same `jti` even for the same account | Allow same `jti` for the same account to resolve idempotently; reject only conflicting contexts. |
| Duplicate accounts or reissued credentials | Account key not unique or credentials returned on `resolved` | Enforce unique `(iss, human.id)` in DB; return credentials and welcome email only on `created`. |

### Context guide and transport

| Symptom | Cause | Fix |
| :--- | :--- | :--- |
| Context hash mismatch | Guide updated without updating `context.sha256` | Deploy updated guide bytes and new `context.sha256` together. |
| Broker rejects receipt `context` pointer | Cross-domain URL or missing `service.provider_url` | Host guide on the signup endpoint's registrable domain and include `service.provider_url`. |
| `404` on `/.well-known/agent-signup.json` | Host hides dotfiles or framework rewrites route | Add an explicit route (for example `app/.well-known/agent-signup.json/route.ts`). |
| CDN challenge HTML returned | Bot protection enabled on well-known or signup route | Exempt `/.well-known/agent-signup.json`, `terms.url`, and `endpoints.agent_signup` from interactive challenges. |
| Signup credential cached by CDN | Missing `Cache-Control: no-store` | Send `Cache-Control: no-store` on every `POST` signup response. |

## Diagnostic sequence

When debugging a broken provider setup, run these six checks in order:

1. `curl -sS -D - https://<origin>/.well-known/agent-signup.json` to confirm `200`, `application/json`, and no redirects.
2. Fetch `terms.url` twice and compare `sha256sum` to confirm deterministic bytes.
3. Run `npx @agentregistrar/discovery@2.1.1 validate https://<origin>/.well-known/agent-signup.json --probe-jwks --json` and inspect `errors`.
4. Run **Test my setup** in the [Provider Portal](/providers/portal/#3-step-setup-wizard) to inspect the unsigned signup probe and assertion preview.
5. Verify `<iss>/.well-known/jwks.json` is reachable from your backend and matches `kid`/`EdDSA`.
6. Replay a local fixture assertion from [Verify assertions](/providers/guides/verify-assertions/) and confirm exact status and error codes against [Error codes](/reference/error-codes/).
