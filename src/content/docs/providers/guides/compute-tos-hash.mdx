**Goal:** serve one complete agreement at `terms.url` with stable bytes, and
understand when a digest is computed and compared.

Spec `v2.0.0` moved the terms out of `/.well-known/agent-signup.json`. Discovery
carries `terms: { version, url }`; it no longer carries `terms.text` or
`terms.sha256`. At signup the Broker fetches `terms.url`, hashes the exact
response bytes as `sha256:<64 lowercase hex>`, and records that value in the
assertion `delegation.accepted_rp_tos_hash` and in the ToS ledger. The provider
checks `delegation.accepted_rp_tos_url` and may also check the digest when it
serves deterministic bytes. The normative rule is
[ToS binding](/agent-identity/v1/specification/#6-tos-binding).

## Serve stable bytes

The URL in discovery is the terms document. Treat it as a file, not a page that
changes on every request.

- Serve the same bytes for the same version. No per-request nonce, challenge
  token, timestamp, locale, A/B variant or session-specific wrapper.
- Do not rely on a redirect. The Broker follows up to three same-origin
  redirects and hashes the bytes of the final response.
- Prefer `text/plain; charset=utf-8` for the agreement itself. If you render
  HTML, keep the agreement text byte-identical between requests and note that
  the digest covers the whole response, markup included.
- Bump `terms.version` whenever the bytes change materially.

## Reproduce the digest

You do not need to publish this value. It is useful when you want to compare the
bytes you serve against the bytes the Broker fetched, or when your signup
handler chooses to verify the optional hash.

Save as `hash.mjs`:

```js
import { createHash } from "node:crypto";
import { readFileSync } from "node:fs";

const bytes = readFileSync("terms.txt");
const hash = "sha256:" + createHash("sha256").update(bytes).digest("hex");
console.log(hash);
```

Run against the file you deploy as your terms document:

```bash
node hash.mjs
```

The shell form is equivalent when the file ends with the same newline:

```bash
sha256sum terms.txt
```

Prefix the digest with `sha256:`. `sha256sum` hashes the file bytes, including a
trailing newline.

## Check what you serve

Fetch the live URL and hash those bytes. This is the value the Broker will
record for the next signup.

```bash
curl -sS https://example.com/terms -o served.txt
sha256sum served.txt
```

Run it twice. The two digests must match. If they differ, the URL is not serving
stable bytes and it is not a usable terms document.

Hashing an HTML page is allowed only when those bytes are stable. A page that
embeds a per-request challenge token, a cache-busting script or a rotating
banner produces a different digest on every fetch, so no one can reproduce what
was accepted.

## Common mistakes

| Mistake | Result |
| :--- | :--- |
| Publishing `terms.text` or `terms.sha256` again | Ignored under `v2.0.0`: `terms` passes through unknown fields, and discovery carries only `version` and `url`. |
| Serving a per-request challenge page | The Broker hashes a different response on each fetch; the digest is not reproducible. |
| Redirecting `terms.url` | The Broker follows up to three same-origin redirects and hashes the final response bytes; a cross-origin redirect fails the fetch. |
| Hashing a summary while serving the full agreement | The recorded digest covers bytes the human was not shown. |
| Editing the bytes under the same `terms.version` | An assertion minted for the old version is stale and is rejected. |
| Keeping two terms URLs or two versions in one document | There is one `terms.url` and one `terms.version`. |

## When the terms change

1. Write the new complete agreement.
2. Pick a new `terms.version`.
3. Publish the new bytes at `terms.url` and the new version in discovery
   together.
4. The Broker fetches `terms.url` at the next signup and records a new hash.
5. An assertion that carries an old `accepted_rp_tos_url` or an old terms version
   is a stale-terms hard stop. The agent re-discovers and re-accepts.

A grace period, if you have one, is documented outside discovery and applies to
assertions already in flight, not to the advertised value.

## Verify

Run the validator against your discovery document and fetch the terms URL:

```bash
pnpm --silent validate:discovery https://example.com/.well-known/agent-signup.json --json
curl -sS -o /dev/null -w '%{http_code} %{content_type}\n' https://example.com/terms
```

A passing run reports `"valid": true` and no errors. The v2.0.0 validator does
not require or report `terms.text` or `terms.sha256`. See the
[conformance validator](/agent-identity/v1/validator/).
