After verifying an assertion and creating or resolving an account, your signup endpoint may optionally return two additional fields:

1. **`signup_token` (Contract E):** An RP-signed receipt proving who signed up, for which service, under which terms hash, and when.
2. **`context`:** A hash-pinned pointer `{ url, sha256 }` to your post-signup vendor documentation (`SKILL.md`).

Both fields are optional. Base signup conformance stays **keyless**: accepting agent signups requires no provider signing key because broker-managed attestations support `keys: []`. Receipts remain strictly RP-signed (there is no unsigned or API-key receipt tier) so attribution and abuse-report standing stay cryptographically verifiable by any federated broker. Keyless signups remain fully conformant and appear in developer and provider ledgers as **Assertion minted (unconfirmed)** or **Agent-reported** until you register an Ed25519 key in the [Provider Portal Credentials tab](/providers/portal/#credentials-tab) and adopt signed receipts.

See [Receipt and context](/protocol/receipt-and-context/) for the full normative field schema and [spec section 11](/protocol/specification/#11-contract-e-identity-facts--the-context-pointer) for the `v2.3.0` asynchronous Contract F profile.

## Signup receipt claims (Contract E)

A signup receipt is signed by **your** registered Ed25519 relying-party key - never by the broker. That key must appear with the `receipt` purpose in the exact provider attestation named by `service.attestation_jti`.

| Claim | Requirement |
| :--- | :--- |
| `iss` | Your canonical origin (for example `https://example.com`). Must equal `service.origin`. |
| `sub` | The agent ID (`agt_...`) from the verified assertion. |
| `aud` | The human broker origin (for example `https://agentregistrar.dev`). |
| `jti` | Unique receipt ID (`srp_` + 26-character lowercase Crockford base32 ULID). |
| `iat`, `signed_up_at` | Unix seconds. Both must fall within the named attestation's `[iat, exp]` window. |
| `assertion_jti` | The `jti` of the assertion presented at signup. |
| `service.audience` | Your published `audience`. |
| `service.origin` | Your canonical origin; must equal `iss`. |
| `service.provider_name` | Your `provider_name`. |
| `service.provider_url` | Canonical URL on the same registrable domain as `endpoints.agent_signup` (required when `context` is present). |
| `service.account_id` | Opaque account reference in your system (not a resource inventory or SKU). |
| `service.attestation_jti` | Exact `jti` of the attestation containing the signing key. |
| `service.key_id` | Key ID signing the receipt; must match JWS header `kid`. |
| `agent.*` | `id`, `name`, `email` from the verified assertion. |
| `human.*` | `id`, `name`, `email`, `verified` from the verified assertion. |
| `tos.*` | `version`, `url`, `sha256`, and optional `master_tos_version`. `tos.sha256` MUST equal `delegation.accepted_rp_tos_hash` from the verified assertion. |
| `context` | Optional `{ url, sha256 }` pointer to your post-signup guide. |
| `exp` | **Omit.** Receipts do not expire; validity is evaluated historically against the named attestation window. |

Do not put SKUs, provisioning URLs, credentials, or free-form resource metadata in the receipt.

## Sign a receipt

Save as `sign-receipt.mjs` (`npm install jose`). Keep `rp-private.jwk.json` in your secret manager, and keep the exact `attestation.jws` that was active at signing time:

```js
import { readFileSync } from "node:fs";
import { importJWK, SignJWT } from "jose";

const privateJwk = JSON.parse(readFileSync("rp-private.jwk.json", "utf8"));
const attestation = readFileSync("attestation.jws", "utf8").trim();
const attPayload = JSON.parse(Buffer.from(attestation.split(".")[1], "base64url").toString("utf8"));

const key = attPayload.keys.find((candidate) => candidate.kid === privateJwk.kid);
if (!key || !key.purposes.includes("receipt")) {
  throw new Error("Signing key is not an active receipt key in this attestation");
}

const now = Math.floor(Date.now() / 1000);
if (now < attPayload.iat || now > attPayload.exp) {
  throw new Error("Attestation is not valid at signing time");
}

const signupToken = await new SignJWT({
  iss: attPayload.rp.origin,
  sub: "agt_01j00000000000000000000000",
  aud: "https://agentregistrar.dev",
  jti: "srp_01j00000000000000000000000",
  iat: now,
  signed_up_at: now,
  assertion_jti: "jti_01j00000000000000000000000",
  service: {
    audience: attPayload.rp.audience,
    origin: attPayload.rp.origin,
    provider_name: "Example Provider",
    provider_url: "https://example.com",
    account_id: "acct_opaque_0001",
    attestation_jti: attPayload.jti,
    key_id: privateJwk.kid,
  },
  agent: {
    id: "agt_01j00000000000000000000000",
    name: "coding-agent",
    email: "coding-agent@agents.example",
  },
  human: {
    id: "hum_01j00000000000000000000000",
    name: "Example Human",
    email: "human@example.com",
    verified: true,
  },
  tos: {
    version: "2026.1",
    url: "https://example.com/terms",
    sha256: "sha256:6c18126f93de8d1972589ca94633ca82e76bd9ba1f0592618b0105753f3501d6",
    master_tos_version: "2026.1",
  },
  context: {
    url: "https://example.com/docs/SKILL.md",
    sha256: "sha256:a3307e1b3904c7671f341730017f21bed656a85241b645c854b4f2887e7976ac",
  },
})
  .setProtectedHeader({
    alg: "EdDSA",
    typ: "agent-signup-receipt+jwt",
    kid: privateJwk.kid,
  })
  .sign(await importJWK(privateJwk, "EdDSA"));

console.log(signupToken);
```

## Return and record the receipt

Return `signup_token` and optional `context` in your signup response alongside any show-once creation credential:

```json
{
  "resolution": "created",
  "account_id": "acct_opaque_0001",
  "api_key": "sk_live_show_once_credential",
  "signup_token": "<compact JWS>",
  "context": {
    "url": "https://example.com/docs/SKILL.md",
    "sha256": "sha256:a3307e1b3904c7671f341730017f21bed656a85241b645c854b4f2887e7976ac"
  }
}
```

Two recording paths exist:

### Discover `signup_receipt_endpoint` (Contract I, `v2.3.0`)

Instead of hardcoding a broker receipt path, discover `signup_receipt_endpoint` from the human broker's metadata document at `GET <broker_issuer>/.well-known/agent-broker.json` (where `<broker_issuer>` is the verified assertion's `iss`):

```ts
export async function resolveSignupReceiptEndpoint(brokerIssuer: string): Promise<string> {
  const origin = new URL(brokerIssuer).origin;
  const fallback = `${origin}/api/broker/signup-receipt`;

  try {
    const res = await fetch(`${origin}/.well-known/agent-broker.json`, {
      headers: { Accept: "application/json" },
    });
    if (!res.ok) return fallback;
    const meta = (await res.json()) as {
      issuer?: string;
      signup_receipt_endpoint?: string;
    };
    if (meta.issuer !== origin || typeof meta.signup_receipt_endpoint !== "string") {
      return fallback;
    }
    const endpoint = new URL(meta.signup_receipt_endpoint);
    if (endpoint.protocol !== "https:" || endpoint.username || endpoint.password) {
      return fallback;
    }
    return endpoint.toString();
  } catch {
    return fallback;
  }
}
```

Cache the discovered URL per broker issuer in memory (for example 15 minutes). Cross-origin `signup_receipt_endpoint` values are permitted by Contract I under standard SSRF checks (rejecting private, loopback, and link-local addresses), though same-origin is recommended. When a broker omits `signup_receipt_endpoint` or metadata is unavailable, fall back to `<broker_issuer>/api/broker/signup-receipt`.

### Asynchronous server-to-server callback (Contract F, recommended)

For strongest attribution (`proof_source: "rp_callback"`, shown as **Confirmed (provider-signed)** / **Provider-reported** in the portal) without adding broker latency to your signup endpoint, deliver Contract F receipts asynchronously from a durable outbox:

1. Persist the local account inside your `POST endpoints.agent_signup` handler.
2. Sign the Contract E `signup_token` using your active Ed25519 key and the exact `rp_attestation` JWS active at signing time.
3. Enqueue `{ signup_token, rp_attestation, receipt_endpoint }` in a durable outbox table keyed by `signup_token_jti`.
4. Return `201` (or `200` on resolve) immediately to the agent with `signup_token` and optional `context`.
5. Trigger a best-effort background `POST` to `receipt_endpoint` (for example with `waitUntil` or `after()`), backed by a periodic retry worker sweeping pending rows.

```bash
curl -sS -X POST https://agentregistrar.dev/api/broker/signup-receipt \
  -H "Content-Type: application/json" \
  -d '{"signup_token":"<compact JWS>","rp_attestation":"<exact attestation JWS>"}'
```

- Always store and send the **exact historical attestation** named by `service.attestation_jti`. Never substitute a newer renewed attestation; because Contract E receipts are verified historically against the attestation's `[iat, exp]` window at signing time, delayed retries succeed cleanly even after attestation renewal or expiry.
- Receipts are idempotent forever on `jti`. Delivering a new `rp_callback` receipt also emits a [`signup.confirmed` webhook](/providers/webhooks/#subscribable-events) if you subscribe to it (or `signup.conflict` if an account mismatch is detected).

#### Contract F retryability matrix

Classify every Contract F response in your outbox worker as follows:

| Outcome / HTTP status | `code` (when present) | Outbox action |
| :--- | :--- | :--- |
| Network error / timeout | - | **Retry** with exponential backoff. |
| `429` | `rate_limited` | **Retry** with exponential backoff; honor `Retry-After` when present. |
| `503` | `rp_broker_unavailable` | **Retry** with exponential backoff (transient trusted-broker metadata or JWKS outage). |
| Other `5xx` | - | **Retry** with exponential backoff. |
| `200` / `201` | - | **Terminal** (delivered or `deduplicated: true`; mark complete). |
| `400` | `invalid_request` | **Terminal** (do not retry; fix malformed JSON or missing fields). |
| `401` | `invalid_attestation`, `rp_broker_untrusted`, `invalid_signup_token`, `attestation_not_valid_at_signing`, `attestation_unavailable` | **Terminal** (do not retry; cryptographic, trust, or historical-window rejection). |
| `409` | `signup_conflict` | **Terminal** (do not retry; same `jti` submitted with a conflicting body). |

### Agent-carried receipt via MCP

The agent can also record your signed receipt by calling `identity_record_signup` with `{ signup_token, rp_attestation? }`. That tool accepts signed receipts only and records `proof_source: "rp_signed"` (**Provider-signed**). If `rp_attestation` is omitted, the broker fetches your discovery attestation and requires its `jti` to match `service.attestation_jti`.

### Idempotent resolve behavior

- On `resolution: "resolved"`, omit the provider credential and do not send duplicate welcome or legal emails.
- You may issue a fresh `signup_token` on resolve so a dropped-response retry can still record attribution.
- Never use the receipt `jti` as your account primary key.

## Post-signup context guide

Use the optional `context` pointer to hand agents a Markdown or plain-text guide (`SKILL.md`) covering everything intentionally kept out of discovery: authentication with your API key, base URLs, provisioning examples, SKUs, quotas, vendor error codes, credential rotation, and support contact.

### Context pointer rules

| Rule | Requirement |
| :--- | :--- |
| URL | Absolute HTTPS URL on the **same registrable domain** as `endpoints.agent_signup` (`localhost` allowed for development only). |
| Hash | `sha256:<64 lowercase hex>` computed over the exact UTF-8 bytes served at `context.url`. |
| Content type and size | `text/markdown; charset=utf-8` or `text/plain; charset=utf-8`; 1 MiB recommended maximum. |
| Security boundary | Never include API keys, secrets, or protocol discovery fields. The broker validates the pointer statically and never fetches `context.url`. |
| Receipt pairing | Include `service.provider_url` on the same domain in signed receipts so the broker can verify domain binding. |

### Minimal `SKILL.md` skeleton

```markdown
# Example Provider agent guide

Untrusted vendor documentation. Version 1.0.0, updated 2026-11-22.

## Authentication
Send `Authorization: Bearer <provider api_key>`.

## Provisioning
POST https://example.com/api/v1/resources

## Limits and errors
Document vendor rate limits, quotas, and retry guidance here.

## Credential recovery
Explain how the human owner or agent rotates a lost credential. Repeated signup resolves the account without reissuing a key.

## Support and abuse
security@example.com
```

### Compute and verify the guide hash

Compute `context.sha256` from the exact deployed bytes and ship bytes and hash together in the same deploy:

```bash
curl -sS https://example.com/docs/SKILL.md -o SKILL.md
sha256sum SKILL.md
```

Prefix the 64-character hex digest with `sha256:`. If a guide changes while your signup response still returns the old hash, agents that verify the digest will stop cleanly rather than trusting altered instructions.
