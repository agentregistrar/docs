`GET /.well-known/agent-signup.json` tells agents which brokers your service trusts, which scopes are required, where your terms live, and where to send a signup assertion. It is an identity parameter document, not a product catalog.

If you use the [Provider Portal](/providers/portal/), Step 2 of the setup wizard generates this JSON for you. Use this guide when authoring or hosting the document yourself.

## Identity-only discovery document

This document passes the `v2.1.0` conformance validator with zero errors and zero warnings (`example.com` and `example-provider` are synthetic values):

```json
{
  "protocol": "agent-identity-protocol",
  "protocol_version": "2.0",
  "audience": "example-provider",
  "provider_name": "Example Provider",
  "provider_url": "https://example.com",
  "contact": "security@example.com",
  "updated_at": "2026-11-22T00:00:00Z",
  "issuer_allowlist": ["https://agentregistrar.dev"],
  "required_scopes": ["tos:accept"],
  "terms": {
    "version": "2026.1",
    "url": "https://example.com/terms"
  },
  "endpoints": {
    "agent_signup": "https://example.com/api/signup/agent"
  },
  "attestation": {
    "mode": "broker",
    "uri": "https://agentregistrar.dev/api/broker/provider-verification?origin=https%3A%2F%2Fexample.com&audience=example-provider"
  },
  "extensions": {
    "com.example": {
      "status_page": "https://status.example.com"
    }
  }
}
```

### What stays out of discovery

Do not include product catalogs, SKUs, pricing tiers, quotas, provisioning endpoints, OTP/email-signup routes, or credentials anywhere in `agent-signup.json` - including under `extensions`. The validator rejects vendor capability fields at any nesting depth.

Use `extensions` only for reverse-DNS non-capability metadata such as a status page or support URL. Product APIs and usage guides belong in an optional post-signup [context guide](/providers/guides/issue-signup-receipt/#post-signup-context-guide). See [Discovery fields](/protocol/discovery-fields/) and [Scope boundaries](/protocol/scope-boundaries/) for normative field definitions.

Upgrading an older `v1.x` or `v2.0.0` document? See the [protocol changelog](/protocol/changelog/) for breaking changes (including `protocol: "agent-identity-protocol"`, `protocol_version: "2.0"`, URL-hosted `terms`, and replacing embedded `rp_attestation` with `attestation: { mode, uri }`).

## Serve stable terms at `terms.url`

Discovery carries `terms: { version, url }` only - never `terms.text` or `terms.sha256`. At signup, the broker fetches `terms.url` directly, computes `sha256:<64 lowercase hex>` over the exact UTF-8 response bytes, and writes that digest into `delegation.accepted_rp_tos_hash` and the human's audit record.

Treat `terms.url` as a static file:

- **Serve deterministic bytes:** No per-request nonce, challenge token, timestamp, locale negotiation, or A/B banner.
- **Prefer plain text:** `text/plain; charset=utf-8` keeps diffs clean. HTML is allowed if the bytes stay identical across fetches; note that the broker hashes the entire response body, markup included.
- **Avoid redirects:** The broker follows at most three same-origin redirects and fails cross-origin redirects.
- **Update atomically:** When your terms change materially, publish the new bytes at `terms.url` and bump `terms.version` together. Never edit the agreement under the same version string.

Verify byte stability before publishing by fetching the live URL twice:

```bash
curl -sS https://example.com/terms | sha256sum
curl -sS https://example.com/terms | sha256sum
```

Both digests must match. If they differ, agents and verifiers cannot reproduce what was accepted.

## Terms accountability and retention

When an agent signs up, two agreements apply: the human owner's master delegation agreement with the broker (`delegation.master_tos_version`), and your terms at `terms.url` (`delegation.accepted_rp_tos_url`, `delegation.accepted_rp_tos_hash`, `delegation.accepted_at`).

This proves an allowed broker vouched for a verified human email and recorded the exact bytes fetched at `terms.url`. It does not prove the human read every clause or guarantee agent conduct; see [Trust and limits](/start/trust-and-limits/).

Retain enough audit fields per signup to answer who signed up, for whom, under which terms, and when:

- **Store:** assertion `jti`, `iss`, `agent.id`, `human.id`, your opaque `account_id`, `terms.version`, `delegation.accepted_rp_tos_url`, `delegation.accepted_rp_tos_hash`, `delegation.accepted_at`, optional receipt `jti`, and outcome (`created` or `resolved`).
- **Do not log:** provider credentials, unnecessary raw assertion JWTs past verification, or full terms text on every log line.

## Optional attestation source modes

The `attestation` object lets clients verify your domain ownership before sending an assertion. Three configurations are conformant:

| Mode | Discovery field | Behavior and trade-offs |
| :--- | :--- | :--- |
| **Broker-managed (default)** | `attestation: { mode: "broker", uri: "<broker>/api/broker/provider-verification?origin=...&audience=..." }` | Recommended. Keyless by default (`keys: []` supported), auto-renewed on demand with no cron job or redeploy. Typed broker status responses (`403` suspended, `410` revoked, `404` unverified) report lifecycle state cleanly. Accepted by both `verify` and `strict` clients. |
| **Provider-managed (opt-in)** | `attestation: { mode: "provider", uri: "https://<origin-or-subdomain>/..." }` | Self-hosted JSON document `{ "attestation": "<JWS>" }` on your discovery origin or a subdomain. Carries a 24-hour TTL; renew on a 12-hour target via `POST /api/provider/v1/attestation`. Rejected by `strict` clients because revocation lags until expiry. |
| **Omitted** | No `attestation` field | Conformant and **unverified**. Works for `no_verify` clients; refused by default `verify` and `strict` clients. |

Verification proves domain control (or legal-entity evidence where reviewed), not product safety or endorsement.

## Transport rules

| Rule | Requirement |
| :--- | :--- |
| Method and path | `GET /.well-known/agent-signup.json` |
| Status when supported | `200` (`404` or `410` when unsupported; never `401` or `403`) |
| Content type | `application/json` |
| Authentication and redirects | None (exempt from CDN bot challenges and login walls) |
| Cache header | `Cache-Control: public, max-age=60` (maximum `300`) |
| CORS | `Access-Control-Allow-Origin: *` where appropriate |
| Body size | At most 1 MiB |
