Report a compromised or abusive agent sub-identity to the broker using Contract D.2 (`POST /api/broker/report-abuse`). Reports are cryptographically authenticated so the broker can attribute the report to your verified service, open a case, and apply a protective suspension pending operator review where standing is verified.

Contract D.2 requires an active Ed25519 RP signing key registered with the `abuse` purpose in the [Provider Portal Credentials tab](/providers/portal/#credentials-tab) and a **current** provider attestation. Do not use it for billing disputes, ordinary support, or routine account cancellations.

## Request shape

`POST https://agentregistrar.dev/api/broker/report-abuse` accepts JSON up to 64 KiB containing exactly two compact JWS strings:

```json
{
  "rp_attestation": "<compact current provider attestation JWS>",
  "report": "<compact signed report JWS>"
}
```

### `report` JWS header and claims

Protected header: `{ "alg": "EdDSA", "typ": "agent-rp-abuse+jwt", "kid": "<your rp key id>" }`.

| Claim | Required | Meaning |
| :--- | :--- | :--- |
| `iss` | yes | Your canonical RP origin (must equal `rp.origin` in `rp_attestation`). |
| `aud` | yes | The human broker origin (for example `https://agentregistrar.dev`). |
| `jti` | yes | Unique report ID (`abr_` + 26-character lowercase Crockford base32 ULID). |
| `iat`, `exp` | yes | Unix seconds with `exp - iat` equal to exactly `300` seconds (5 minutes). |
| `agent_id` | yes | The `agent.id` (`agt_...`) from the verified assertion or receipt. |
| `reason` | yes | 1 to 500 characters of factual description. |
| `evidence` | no | Optional `{ "assertion_jti": "...", "signup_token_jti": "..." }`. |

The signing key named by `kid` must appear in the attached `rp_attestation` `keys[]` array with `abuse` in its purposes, and `rp_attestation` must be **current at report time** (within 60 seconds of clock skew).

## Broker verification steps

When a report arrives, the broker:

1. Parses `rp_attestation` and requires `typ: "agent-rp-attestation+jwt"`, `alg: "EdDSA"`, and one `kid`.
2. Checks `rp_attestation` `iss` against the broker's trusted RP-broker list before making any JWKS fetch.
3. Verifies `rp_attestation` against the RP broker's JWKS and enforces `[iat, exp]` with 60 seconds of skew.
4. Confirms `rp.origin` and `rp.audience` match the provider's recorded discovery binding.
5. Verifies `report` using the named `abuse` key, then checks `iss`, `aud`, and the 300-second freshness window.

Transient RP-broker JWKS or metadata outages return retryable `503 rp_broker_unavailable`, never an authentication failure.

## Verified versus unverified standing

| Condition | `verification_status` | Broker action |
| :--- | :--- | :--- |
| Verified attestation plus a linked signup with `proof_source` `rp_callback` or `rp_signed` | `verified` | Opens an abuse case and may apply a protective suspension pending operator review and notify the human owner. |
| Verified attestation with no linked signup receipt (or only `agent_self_reported` / legacy link) | `unverified` | Opens an abuse case for review; does **not** suspend the agent. |
| Missing, expired, invalid, untrusted, or unavailable attestation | rejected | Returns an error and opens no case. |

A protective suspension is temporary and pending operator review - it is not a legal adjudication. Only a broker operator can restore a suspended agent (the human owner cannot clear a protective suspension with the ordinary kill switch).

## Responses and limits

An accepted new report returns `202`:

```json
{
  "case_id": "0d5f6a7c-...",
  "report_jti": "abr_01j...",
  "verification_status": "verified",
  "deduplicated": false,
  "agent_suspended": true,
  "human_notified": true
}
```

- **Idempotent replay:** Repeating the same `jti` with the same payload returns `200` with `deduplicated: true` and the original `case_id`. Reusing a `jti` with a different payload returns `409`.
- **Unsigned body:** Returns `401` with `code: "unauthenticated_report"`.
- **Rate limit:** 60 requests per minute per IP (`429 rate_limited`).

## Scope and boundaries

- **What the broker does:** Authenticates the provider, verifies receipt standing, records the case and timeline, notifies the operator, and (when verified and receipt-linked) may suspend the agent identity to stop new assertions and inbox access.
- **What the broker does not do:** Adjudicate disputes, issue refunds, delete accounts or resources on your service, or invalidate already-minted short-lived assertions before `exp`. Always apply your own account suspension, credential revocation, and rate limits immediately.
- **Evidence minimization:** Send only the minimum facts needed (`agent_id`, relevant timestamps, `assertion_jti` or `signup_token_jti`, factual `reason`). Never include API keys, passwords, payment data, or full request dumps.

## Human reports about a provider

Contract D.2 is strictly for providers reporting an agent. A human developer who needs to report a misbehaving provider does so from the [Developer Portal](/agents/portal/), which calls the session-authenticated `POST /api/broker/report-provider` path and lets that human update their own local trust settings.
