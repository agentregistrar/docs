**Goal:** prove the document conforms, then get the implementation listed with reproducible evidence.

The validator reference is [Conformance validator](/agent-identity/v1/validator/). The registry criteria and the entry schema are in the [implementation registry](https://github.com/agentregistrar/spec/blob/main/registry/README.md).

## Run the validator

From a clone of the spec repository:

```bash
git clone https://github.com/agentregistrar/spec
cd spec
pnpm install
pnpm --silent validate:discovery https://example.com/.well-known/agent-signup.json --json
```

From any project, using the published package. There is no `bin` entry, so invoke the TypeScript source with `tsx`:

```bash
npm install @agentregistrar/discovery@1.1.0 tsx@4.23.15
npx tsx node_modules/@agentregistrar/discovery/src/validate-discovery.ts \
  https://example.com/.well-known/agent-signup.json --json
```

File mode needs no network:

```bash
pnpm --silent validate:discovery ./agent-signup.json --json
```

Use `pnpm --silent` (or `pnpm -s`) so pnpm's banner does not pollute stdout. The validator itself writes only JSON.

## Flags and exit codes

| Flag | Effect |
| :--- | :--- |
| `--json` | Print one machine-readable result on stdout. |
| `--probe-jwks` | Fetch `GET <issuer>/.well-known/jwks.json` for every allowlisted issuer and require at least one verification key. |
| `--probe-endpoints` | Non-destructively `HEAD` then `OPTIONS` the advertised signup endpoint. Never `POST`. |
| `--timeout <ms>` | Per-fetch timeout. |
| `--max-bytes <n>` | Bounded read size. |
| `--help` | Print usage. |

| Exit code | Meaning |
| :--- | :--- |
| `0` | Valid conformant document. Warnings do not change the code. |
| `1` | A document was obtained and parsed, but failed conformance, including a failed opt-in probe. |
| `2` | No usable document: unreadable file, network or timeout failure, redirect problem, non-`200`, wrong content type, size cap or unparseable JSON. |

The distinction matters in CI: `2` is an operational failure, `1` is a document failure. Both are non-zero.

## Registry criteria

To be listed, an implementation must:

1. Pass the identity-only validator with zero errors. Warnings are permitted.
2. Publish a public, stable HTTPS `/.well-known/agent-signup.json` on its canonical origin, not a per-deploy or throwaway URL.
3. Provide a reachable security, abuse or legal contact that someone monitors.
4. Publish a post-signup context guide if it has vendor capabilities to document.

The registry lists protocol capabilities only: `agent_signup` and `post_signup_context`. A catalog, a SKU or a provisioning endpoint is not a registry capability.

Listing is a statement about the discovery document. It is not an endorsement of the product, its security, its uptime or its pricing.

## Submit an entry

1. Make the document conformant using [Publish discovery](/providers/guides/publish-discovery/).
2. Run the validator against the public URL and keep the JSON.
3. Open a pull request against `agentregistrar/spec` that adds one object to the `implementations` array in `registry/implementations.json` with:
   - `name`, `url`, `discovery_url`, `audience`, `protocol`, `capabilities`, `contact`, `validated_at`, `validator_version`;
   - a `validator_evidence` object with the exact command and the resulting counts.
4. Update the table in `registry/README.md` so it stays in lockstep.
5. The pull request is reviewed against the criteria above.

Read `audience` and `protocol` from the validator's `--json` output rather than retyping them. The field reference is in the [validator guide](/agent-identity/v1/validator/).

An entry whose document stops passing is removed or updated with fresh evidence.

## The reference-entry exception

The VaporCloud entry in the registry records the intended production `.example` discovery URL, while the recorded validation ran against the locally started reference implementation. The exception is documented in the registry and is not a precedent. New third-party entries must be publicly re-validatable.
