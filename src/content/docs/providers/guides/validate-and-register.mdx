Validate your discovery document before taking live traffic, optionally verify your provider attestation, and submit your live service to the public implementation registry.

Conformance and verification are **two independent verdicts**: a document can be conformant and unverified (`exitCode: 0`) if it omits `attestation`. See [Conformance validator](/protocol/validator/) for the full CLI flag reference, JSON schema, reason codes, and offline fixture options.

## Run the conformance validator

Validate a live HTTPS discovery URL (or a local JSON file during development) using `@agentregistrar/discovery@2.2.0`:

```bash
npx @agentregistrar/discovery@2.2.0 validate https://example.com/.well-known/agent-signup.json --json
```

Add opt-in non-destructive probes to verify that every issuer in `issuer_allowlist` publishes a valid JWKS and that `endpoints.agent_signup` (plus optional `endpoints.agent_login`) is reachable (`HEAD`/`OPTIONS`, never `POST`):

<ValidatorPersonalizer includeProbes />

```bash
npx @agentregistrar/discovery@2.2.0 validate https://example.com/.well-known/agent-signup.json \
  --probe-jwks --probe-endpoints --json
```

If you are working from a clone of `agentregistrar/spec`, run `pnpm --silent validate:discovery <url-or-file> --json` (pass `--silent` so pnpm's banner does not mix into JSON output).

### Check your attestation (opt-in)

To fetch `attestation.uri` and verify the provider verification credential against a trusted broker:

<ValidatorPersonalizer forceVerifyAttestation />

```bash
npx @agentregistrar/discovery@2.2.0 validate https://example.com/.well-known/agent-signup.json \
  --verify-attestation \
  --trusted-rp-broker https://agentregistrar.dev \
  --json
```

Add `--require-attestation` in CI if you want any non-`verified` attestation (`unverified`, `expired`, `suspended`, `invalid`, or `unavailable`) to fail the run. Never add a broker origin to `--trusted-rp-broker` unless you explicitly trust it; the validator checks the trust list before any JWKS fetch.

### Reading exit codes

- **`0`:** Document fetched, parsed, and conformant (and verified if `--require-attestation` was set).
- **`1`:** Conformance error (malformed JSON, forbidden capability field, invalid `attestation` shape or host binding) or failed attestation under `--require-attestation`.
- **`2`:** Operational fetch or read failure (DNS, TLS, redirect, non-`200`, wrong content type, oversize body, or source/JWKS unavailable under `--require-attestation`).

For the full status-to-exit matrix and every `attestation.reason` code, see [Conformance validator](/protocol/validator/).

## Submit to the public registry

The public [implementation registry](https://github.com/agentregistrar/spec/blob/main/registry/README.md) lists conformant services with reproducible validator evidence.

### Identity-only and non-endorsement boundary

Registry entries list protocol capabilities only: `agent_signup` and `post_signup_context`. Catalogs, SKUs, pricing, and provisioning APIs do not belong in the registry.

Listing is a factual statement that the discovery document passed validation at `validated_at`. It is **not** an endorsement of the product, its security, its uptime, or its conduct. Likewise, an optional verification snapshot proves domain or entity control at `checked_at` and does not certify safety. See [Trust and limits](/start/trust-and-limits/).

### Entry criteria

1. Live `GET /.well-known/agent-signup.json` on a stable canonical HTTPS origin (no throwaway or per-deploy URLs) exits `0` with zero errors.
2. Monitored security, abuse, or legal `contact` published in discovery.
3. Optional post-signup context guide if your service documents vendor capabilities.
4. Optional five-field `verification` snapshot if claiming verified status.

### Optional verification snapshot

To include verified status in your registry entry, add all five fields from a live check at `checked_at`:

```json
"verification": {
  "broker": "https://agentregistrar.dev",
  "level": "domain",
  "attestation_jti": "rpa_01j...",
  "checked_at": "2026-11-22T00:00:00Z",
  "status": "active"
}
```

- `level` is `domain` or `entity`.
- `status` is `active`, `suspended`, or `revoked` at `checked_at`.
- The registry is a static **snapshot**, not a live status feed. Only entries with `status: "active"` at `checked_at` display a verified badge, separate from the conformance badge.

### Pull request steps

1. Run `@agentregistrar/discovery@2.2.0 validate` against your public HTTPS URL with `--json` and save the output.
2. Open a pull request against `agentregistrar/spec` adding one object to `implementations` in `registry/implementations.json` with `name`, `url`, `discovery_url`, `audience`, `protocol`, `capabilities`, `contact`, `validated_at`, `validator_version`, `validator_evidence`, and optional `verification`.
3. Update the table in `registry/README.md` to stay in lockstep.
4. Run `pnpm --silent validate:registry registry/implementations.json --json` and confirm it exits `0` with `"valid": true`.

Copy `audience` and `protocol` directly from the validator `--json` output rather than retyping them.
