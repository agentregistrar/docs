This is the shortest conformant path. You host one terms page, generate one
JSON document, serve it over HTTP and validate it. The last step returns a
stable error from a stub signup route. `example.com` and `example-rp` are
synthetic values; replace them with your own origin and audience.

The base flow is free and needs **no broker account, no SDK and no network call
to the broker** to accept an assertion. A provider account is optional and is
required only to become a verified provider, issue authenticated receipts, or
report abuse with standing.

Spec `v2.0.0` keeps the terms with the provider. Discovery carries
`terms: { "version", "url" }`; the Broker fetches `terms.url` at signup and
hashes the exact response bytes. There is no `terms.text`, no `terms.sha256`,
and no manual hash step.

## Before you start

- Node 22 or newer, with `npm` or `pnpm`.
- An HTTPS origin for production. `http://localhost` and `http://127.0.0.1` are the documented development exception.
- A public page where a human can read the agreement you serve at `terms.url`.
- No broker account, no SDK and no network call to the broker are required for
  the conformant path.

## 1. Write the terms and serve them

The complete agreement lives in `terms.txt`. This example is synthetic. Serve
those exact bytes at `https://example.com/terms`; a static file with
`text/plain; charset=utf-8` is enough.

```bash
mkdir provider-quickstart
cd provider-quickstart
cat > terms.txt <<'EOF'
Example RP Terms of Service
Version: 2026.1

These terms govern accounts created through a brokered agent signup. The agent
acts for a verified human owner, and that human owner is bound by these terms.

1. The service is provided as-is, with no uptime guarantee.
2. The human owner is responsible for the agent's actions.
3. Either party may terminate the account at any time.
EOF
```

The content rules are in [ToS binding](/agent-identity/v1/specification/#6-tos-binding). Serve stable bytes: no redirect, no per-request token, no wrapper that changes between fetches. See [Serve terms at a URL](/providers/guides/compute-tos-hash/).

## 2. Generate the document

Save this as `build-discovery.mjs`. It writes the document with the terms URL
and version; the agreement stays on your origin.

```js
import { writeFileSync } from "node:fs";

const document = {
  protocol: "agent-identity-v1",
  audience: "example-rp",
  provider_name: "Example RP",
  provider_url: "https://example.com",
  contact: "security@example.com",
  issuer_allowlist: ["https://agentregistrar.dev"],
  required_scopes: ["tos:accept"],
  terms: {
    version: "2026.1",
    url: "https://example.com/terms",
  },
  endpoints: {
    agent_signup: "https://example.com/api/signup/agent",
  },
};

writeFileSync("agent-signup.json", JSON.stringify(document, null, 2) + "\n");
console.log("wrote agent-signup.json");
```

```bash
node build-discovery.mjs
```

Expected output:

```text
wrote agent-signup.json
```

The generated document:

```json
{
  "protocol": "agent-identity-v1",
  "audience": "example-rp",
  "provider_name": "Example RP",
  "provider_url": "https://example.com",
  "contact": "security@example.com",
  "issuer_allowlist": [
    "https://agentregistrar.dev"
  ],
  "required_scopes": [
    "tos:accept"
  ],
  "terms": {
    "version": "2026.1",
    "url": "https://example.com/terms"
  },
  "endpoints": {
    "agent_signup": "https://example.com/api/signup/agent"
  }
}
```

Every field above is identity-only. The allowed and forbidden fields are in
[Discovery fields](/agent-identity/v1/discovery-fields/). Do not add product
catalogs, SKUs, provisioning endpoints or OTP endpoints.

## 3. Serve it

Save this as `serve.mjs`. The discovery route returns JSON with no
authentication and no redirect; the signup route is a stub that returns one
stable error.

```js
import { createServer } from "node:http";
import { readFileSync } from "node:fs";

const document = readFileSync("agent-signup.json", "utf8");
const terms = readFileSync("terms.txt", "utf8");

const server = createServer((req, res) => {
  if (req.url === "/.well-known/agent-signup.json" && req.method !== "GET") {
    res.writeHead(405, { allow: "GET" });
    return res.end();
  }
  if (req.url === "/.well-known/agent-signup.json") {
    res.writeHead(200, {
      "content-type": "application/json",
      "cache-control": "public, max-age=60",
      "access-control-allow-origin": "*",
    });
    return res.end(document);
  }
  if (req.url === "/terms") {
    res.writeHead(200, { "content-type": "text/plain; charset=utf-8" });
    return res.end(terms);
  }
  if (req.url === "/api/signup/agent" && req.method !== "POST") {
    res.writeHead(405, { allow: "POST" });
    return res.end();
  }
  if (req.url === "/api/signup/agent") {
    // Stub: real verification is in the generic HTTP guide.
    res.writeHead(401, { "content-type": "application/json" });
    return res.end(JSON.stringify({
      error: "invalid_assertion",
      error_description: "Signature or JOSE header verification failed",
      retryable: false,
    }));
  }
  res.writeHead(404, { "content-type": "application/json" });
  res.end(JSON.stringify({ error: "not_found" }));
});

server.listen(3001, "127.0.0.1", () => console.log("listening on http://127.0.0.1:3001"));
```

```bash
node serve.mjs
```

Expected output:

```text
listening on http://127.0.0.1:3001
```

In another terminal, check the transport:

```bash
curl -sS -D - -o /dev/null http://127.0.0.1:3001/.well-known/agent-signup.json
curl -sS -o /dev/null -w '%{http_code} %{content_type}\n' http://127.0.0.1:3001/terms
```

Expected, in part:

```text
HTTP/1.1 200 OK
content-type: application/json
cache-control: public, max-age=60
access-control-allow-origin: *
200 text/plain; charset=utf-8
```

## 4. Validate the document

Two paths are supported. Use the one that fits your project.

Path A, from a clone of the spec repository:

```bash
git clone https://github.com/agentregistrar/spec
cd spec
pnpm install
pnpm --silent validate:discovery http://127.0.0.1:3001/.well-known/agent-signup.json --json --probe-jwks
```

Path B, with the published package in any project. The package has no `bin` entry, so run its TypeScript source with `tsx`:

```bash
npm install @agentregistrar/discovery@2.0.0 tsx@4.23.15
npx tsx node_modules/@agentregistrar/discovery/src/validate-discovery.ts \
  http://127.0.0.1:3001/.well-known/agent-signup.json --json --probe-jwks
```

Both paths use `--probe-jwks`, so both report one probe. Expected from either path, shortened here:

```json
{
  "validator": "agent-identity-v1",
  "validatorVersion": "2.0.0",
  "mode": "url",
  "valid": true,
  "exitCode": 0,
  "protocol": "agent-identity-v1",
  "audience": "example-rp",
  "providerName": "Example RP",
  "errors": [],
  "warnings": []
}
```

The result also carries separate `conformance` and `attestation` objects; a
document with no `attestation` object reports `attestation.status: "unverified"`
and still exits `0`. The exact field reference is in the [conformance
validator](/agent-identity/v1/validator/).

Exit code `0` means valid. `1` means the document was read and rejected; `2`
means it could not be fetched. `--probe-jwks` additionally checks that every
issuer publishes a usable JWKS and does not touch your signup endpoint.

`terms.text` and `terms.sha256` are legacy v1.3 fields. The v2.0.0 validator
accepts and ignores them; discovery carries only the version and the URL, and
the Broker hashes the bytes at `terms.url` at signup.

## 5. Return one stable error

Send a request with a malformed assertion:

```bash
curl -sS -X POST http://127.0.0.1:3001/api/signup/agent \
  -H 'Authorization: Bearer test' \
  -w '\nHTTP %{http_code}\n'
```

Expected output:

```text
{"error":"invalid_assertion","error_description":"Signature or JOSE header verification failed","retryable":false}
HTTP 401
```

The envelope and the fixed code table are in [Stable error codes](/providers/guides/error-codes/). `error_description` is non-normative; agents branch on `error`.

## Optional: the four-step portal setup

A provider account replaces the manual document with a generated one. The
portal flow is four linear steps:

1. **Create service.** Enter three fields: display name, origin and audience.
   The free plan allows one service.
2. **Verify domain.** Publish the HTTPS well-known file or the DNS TXT record
   the portal shows. The first verified origin makes the account active.
3. **Publish discovery.** Copy the generated `/.well-known/agent-signup.json`
   and deploy it. Its `terms` is `{ version, url }` and its default
   `attestation` is broker-managed, so you host no token and run no renewal job.
4. **Test my setup.** One synchronous check validates the live document,
   fetches `terms.url`, checks the broker-managed attestation, probes
   `endpoints.agent_signup` and shows the exact assertion preview. The first
   passing run marks the service live.

No RP key is required. Broker-managed attestations accept `keys: []`, because
accepting agent signups only needs the broker JWKS. Register an Ed25519 RP key
later only if you want RP-signed receipts (Contract F) or authenticated abuse
reporting.

The portal has five tabs: `Services`, `Signups`, `Credentials`, `Team` and
`Settings`. Attestation issuance is not plan-gated, and this release ships no
checkout, pricing page, invoice or DPA.

See [Trust and limits](/start/trust-and-limits/) for why verification is
identity, not safety, and [Validate and register](/providers/guides/validate-and-register/)
for the registry's five-field verification snapshot. Upgrading a v1.2 document?
Follow [Migrate a v1.2 discovery
document](/providers/guides/publish-discovery/#migrate-a-v12-discovery-document).

## Optional: receipt and context

A signup response may include an RP-signed `signup_token` and a hash-pinned
`context` pointer to your guide. Both are optional. The receipt has no
`exp`; a legacy `exp` is ignored. See [Issue a signup
receipt](/providers/guides/issue-signup-receipt/) and [Publish a context
guide](/providers/guides/publish-context-guide/).

## Verify your work

- [ ] `terms` is exactly `{ "version", "url" }` with no `text` or `sha256`.
- [ ] `terms.url` serves stable bytes with no redirect.
- [ ] The discovery route returns `200`, `application/json`, no redirect and no authentication.
- [ ] The validator exits `0` with zero errors.
- [ ] One failing signup request returns a fixed v1 error code.
- [ ] No forbidden vendor field appears at any depth, including under `extensions`.
