`rp_attestation` was removed in `v1.3.0`. A document that still contains it is
non-conformant with reason `rp_attestation_removed`; there is no compatibility
field, embedded fallback, or dual publication. Contract F receipt and abuse
bodies are a different surface and keep the historical field.

`terms.text` and `terms.sha256` were removed in `v2.0.0`. The provider hosts the
agreement at `terms.url`. There is no compatibility field and no dual
publication; publish `{ version, url }` in one deploy.

Unknown additive fields must be ignored by consumers. Producers should put
non-capability metadata under `extensions.<reverse-dns-namespace>` so typos stay
visible. Moving a vendor capability under `extensions` does not make it
conformant.

## The optional attestation source

`attestation` is the only discovery field that describes the provider's
broker-verified identity, and it carries no token. It has exactly two fields:

```json
{
  "attestation": {
    "mode": "broker",
    "uri": "https://agentregistrar.dev/api/broker/provider-verification?origin=https%3A%2F%2Fprovider.example&audience=example"
  }
}
```

- `mode` is exactly `broker` or `provider`. There are no aliases.
- `uri` is a stable, absolute HTTPS URL with no credentials and no fragment.
  `http://localhost` and `http://127.0.0.1` are the development exception.
- A `broker` URI origin must be in the document's `issuer_allowlist` and, when
  the verifier configures one, the trusted-broker list.
- A `provider` URI origin must be the origin of the discovery document the
  verifier actually fetched, or a subdomain of it. A third-party host, including
  a CDN, is rejected.
- The object is closed: `mode` and `uri` are its complete vocabulary.

The URI serves the same source document in both modes, as `application/json`:

```json
{ "attestation": "<compact JWS>" }
```

The JWS is the contract G token (`typ: agent-rp-attestation+jwt`, `alg: EdDSA`)
that binds `rp.origin`, `rp.audience`, the provider identity, the assurance
level, and the public `keys[]`. Additional envelope fields are ignored. A raw
JWT body is rejected.

Rules:

- The attestation `rp.origin` must equal the canonical origin of the discovery
  document the verifier actually fetched.
- `rp.audience` must equal `discovery.audience`.
- The token is public and copyable; the origin and audience binding prevent
  replay on another service.
- It must not carry a terms hash, scopes, endpoints, `provider_url`, account ids,
  prices, or private material. Its `keys[]` may be empty; no RP signing key is
  needed to accept agent signups.
- A conformant document without `attestation` is **unverified**. An expired,
  invalid, suspended, or unavailable source is a verification result, never a
  conformance failure by itself. A malformed object or a failed host binding is a
  conformance error.
- Do not add any other provider-identity or provider-capability field to
  discovery.

Broker-managed is the default and needs no renewal job. Provider-managed is an
opt-in and makes expiry the revocation bound. See [Trust and
limits](/start/trust-and-limits/) and [Verify
assertions](/providers/guides/verify-assertions/) for the policy and verification
steps. If you are a provider and want the credential, see the [provider
quickstart](/providers/quickstart/).

## Forbidden fields

These must not appear at any nesting depth, including under `extensions`:

| Forbidden surface | Examples |
| :--- | :--- |
| Catalogs and commercial surface | `instance_catalog`, SKUs, pricing tiers, free-tier quotas, product specs |
| Provisioning and resource endpoints | `endpoints.provision`, resource endpoints, instance lifecycle |
| Legacy signup endpoints | `endpoints.email_signup`, `endpoints.verify_otp` |
| Broker receipt callback | `endpoints.broker_signup_receipt` |
| Credentials and API usage | resource credentials, vendor API or SDK usage metadata |

A document is a parameter document, not a capability catalog. Vendor capabilities belong in the post-signup context guide. See [Scope boundaries](/protocol/scope-boundaries/) and the normative [5.3](/protocol/specification/#53-forbidden-fields-vendor-capability-surface).

## Terms at a URL

- `terms.url` must serve the complete agreement with stable bytes. No redirect,
  no per-request token, no variant that changes between fetches.
- The Broker fetches `terms.url` at signup and records
  `sha256:<64 lowercase hex>` over the exact response bytes in
  `delegation.accepted_rp_tos_hash` and in the terms ledger.
- The relying party checks `delegation.accepted_rp_tos_url` against its current
  `terms.url` (trailing slashes normalized). It may also check the hash when the
  URL serves deterministic bytes.
- When the terms change, publish the new bytes and a new `terms.version` before
  accepting new signups. A bounded grace period for in-flight assertions is a
  relying-party policy documented outside discovery; it should not exceed 24
  hours.

See [terms binding](/protocol/specification/#6-tos-binding) and [Re-acceptance](/protocol/specification/#61-re-acceptance).

## Minimal conformant example

This document contains only the required identity fields. It passes the current
validator in file mode with zero errors and zero warnings. The optional
`attestation` object is absent, so the document is conformant and
**unverified**.

```json
{
  "protocol": "agent-identity-protocol",
  "protocol_version": "2.0",
  "audience": "example-provider",
  "provider_name": "Example Provider",
  "issuer_allowlist": ["https://agentregistrar.dev"],
  "required_scopes": ["tos:accept"],
  "terms": {
    "version": "2026.1",
    "url": "https://example.com/terms"
  },
  "endpoints": {
    "agent_signup": "https://example.com/api/signup/agent"
  }
}
```

The example is illustrative. Replace the audience, URLs, scopes and terms with the service's own values, and serve the agreement at `terms.url`. The allowlist entry is the live broker origin (`https://agentregistrar.dev`); a provider that accepts a different broker lists that broker's origin instead.

## Known limits

- Discovery carries no terms digest. The Broker computes it from the bytes it fetches at `terms.url`; a digest the provider could not reproduce from a served page would be meaningless.
- Discovery conformance is cheap to publish. A valid document is not a statement about the service's security, uptime or product.
- The document itself is not signed. The optional `attestation` object
  names a signed statement about the provider; it is not a signature over the
  discovery document. Trust in the document comes from TLS plus the issuer
  allowlist; the assertion and the attestation are separately signed.
- Consumers must ignore unknown additive fields, so a producer can add an identity field without a schema change. The validator warns on unknown top-level fields; warnings do not fail conformance.
