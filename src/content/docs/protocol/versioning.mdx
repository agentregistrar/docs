The Agent Identity Protocol separates its name from its wire version. Discovery
carries the name in `protocol` and the version in `protocol_version`. This page
explains how the protocol changes and how the docs site tracks it. The normative
policy is [spec section 13](/protocol/specification/#13-versioning-extension--deprecation-policy).

## Current version

- Protocol name: **Agent Identity Protocol**.
- Wire identifier: `agent-identity-protocol`.
- Wire version: `2.0`, carried in the required `protocol_version` field.
- Specification release: `v2.1.0`, released 2026-11-21.
- Package: `@agentregistrar/discovery` `2.1.0`.
- `v2.1.0` renamed the protocol from `agent-identity-v1` to
  `agent-identity-protocol`, added the required `protocol_version`, and changed
  the attestation audience to `agent-identity-protocol`. The `v2.0.0` release
  moved discovery terms to a provider-hosted `terms: { version, url }` object
  and removed `terms.text` and `terms.sha256` from the required schema. The
  `v1.3.0` release replaced the embedded `rp_attestation` discovery field with
  one optional `attestation` source object. The JWT format, assertion claims and
  Contracts E, F, H and I are unchanged.
- The policy values are `no_verify`, `verify` (default) and `strict`, with `blocked` as a separate action. The old `allow`/`warn`/`require`/`block` values and the `enforced` field are removed.
- A document that omits `attestation` remains conformant. The `v2.0.0` terms requirement applies separately: a document must publish `terms: { version, url }`. A v1.2 document that embedded `rp_attestation` is no longer conformant until it publishes the new object or omits it.

The full release history is in the [changelog](/protocol/changelog/).

## Additive changes

Additive identity fields and clarifications are allowed within wire version
`2.0`. They do not change the `protocol` name, the `protocol_version` value, or
the discovery path.

- Consumers must ignore unknown fields.
- Producers should namespace non-capability vendor metadata under `extensions.<reverse-dns>`.
- An additive change must pass the [scope-boundaries review checklist](/protocol/scope-boundaries/#7-future-change-review-checklist).
- Additive changes are recorded in the specification changelog and the release notes.
- The schema, the JSON Schema and the validator are updated together so they cannot drift.

Vendor catalogs, provisioning endpoints, resource metadata and API-usage documentation are not additive protocol fields at any version. They belong in the post-signup guide.

## Breaking changes

A breaking change must use a new `protocol` value and a new discovery path, for example `agent-signup-v2.json`.

- The current path must not silently change semantics. `v2.0.0` kept the
  protocol id because it changed only the terms carrier and the provider key
  snapshot, not the handshake. `v2.1.0` renamed the id and split the name from
  the wire version; the handshake and assertion format are unchanged.
- A future version should be dual-published during a migration window.
- The public specification URL should be versioned. The optional `spec` field lets agents and humans find the exact document.
- The registry lists implementations by the `protocol` value their discovery document advertises.

## Path policy

The docs site follows the protocol path:

- `/protocol/` is the canonical path for the current version.
- A future major would get its own path decided in the specification; the old `/agent-identity/v2/` example is retired.
- There is no whole-site versioning. Only the protocol family is path-versioned.
- The generated pages under `/protocol/` are pinned to one spec tag and are regenerated by `pnpm sync:spec`.

## Deprecation and release notes

- `v2.1.0` retires the `agent-identity-v1` wire id. A `v2.0.0` or earlier
  document must add `protocol_version: "2.0"` and the renamed `protocol` value.
  Discovery that still carries `terms.text` or `terms.sha256` remains conformant
  because unknown additive fields are ignored. The `v1.3` `attestation` source
  object is unchanged.
- The specification's changelog records every additive change with its date.
- Release notes record the release evidence, the change process and any non-blocking follow-ups.
- The current version has no formal sunset date. A future breaking change would
  be dual-published during a migration window; the current version would stay
  published for that window.
- A deprecation notice, if one is ever needed, belongs in the release notes and at the top of the affected version's landing page. The docs site does not invent a deprecation schedule ahead of the specification.

## Updating the rendered docs

The rendered pages are generated from a pinned tag, never hand-edited. The version-bump runbook is in the docs repository's `AGENT.md`:

1. Confirm the spec tag and release notes exist; read the diff.
2. Update `spec.lock.json` `tag` and let the sync resolve the commit and hashes.
3. Run `pnpm sync:spec`; review the generated diff for normative changes.
4. Update the hand-authored protocol pages if fields, errors or claims changed.
5. Update the changelog and any current-version strings.
6. Run the build, check, lint and theme gates; verify the schema `$id`.
7. Commit the lock, the generated pages and the hand-authored changes together.

## Known limits

- There is no formal deprecation timetable for the current version.
- The wire version is major-only, so an agent cannot tell additive spec releases
  apart from `protocol_version` alone. The optional `spec` field is the exact
  release pointer.
- The docs site renders one pinned tag. A newer tag is not live until the sync and review land.
