The demo network is a deployed test environment for the Agent Identity Protocol (`v2.1.0`, wire `protocol_version: "2.0"`). It pairs two brokers with three test providers so you can compare same-broker, cross-broker, and unverified signup paths live, alongside the VaporCloud reference provider at [skdl.dev](https://skdl.dev).

Broker B, the three demo providers, and VaporCloud are **simulated third parties** operated by Agent Registrar. They are not independent adopters, not production services, and carry no provisioning, billing, SLA, uptime, or endorsement claims. Use only test data; provider terms describe test services only. Re-run the validation commands below before relying on any live output.

<Aside type="note" title="What is real">
A demo signup creates a real terms acceptance record under your human identity in Broker A (`/activity`). The provider account, credential, and provider-side data are test-only and may be reset.
</Aside>

## Roles and trust

| Host | Role | Registered with | Attestation | What to expect |
| :--- | :--- | :--- | :--- | :--- |
| [Broker A](https://agentregistrar.dev) | Human/agent broker | Home broker | n/a | Your human identity, agent, trust policy, and `/activity` audit trail |
| [Broker B](https://agentregistrardemobroker.com/.well-known/agent-broker.json) | Provider broker | RP-only demo broker | B issues the P2 attestation | Metadata, JWKS, and signed status; does not register agents |
| [P1](https://verifiedprovider1.agentregistrardemorp.com/.well-known/agent-signup.json) | Verified provider | A | A, broker-managed | `verified` in A; A-attested signed receipt can be recorded |
| [P2](https://verifiedprovider2.agentregistrardemorp.com/.well-known/agent-signup.json) | Verified provider | B | B issues; P2 hosts | `verified` after you trust B in `/trust`; B-attested receipt can be recorded |
| [P3](https://unverifiedprovider1.agentregistrardemorp.com/.well-known/agent-signup.json) | Unverified provider | Neither | None | Unverified; `no_verify` proceeds, `verify` and `strict` block, `blocked` always refuses |
| [Landing](https://agentregistrardemorp.com) | Demo status page | None | None | Host links and live status; no protocol identity |

A verified provider publishes an optional `attestation` source object in discovery, never the token itself: P1 uses broker-managed mode via A, and P2 uses provider-managed mode where B issues the token and P2 hosts the source document on its own origin. P3 publishes no `attestation` object.

P1, P2, and P3 share the registrable domain `agentregistrardemorp.com`. Their origins and audiences are separate, though they are not isolated from each other at the DNS boundary.

### Topology

<DemoNetworkDiagram variant="topology" />

Your human account and agent live on Broker A. P1 is registered with A, P2 is registered with B, and P3 is registered with neither. All three providers accept assertions from A. A trusts B for your account only when you add B under federated broker trust in `/trust`; A and B have no shared account.

### Cross-broker sequence

<DemoNetworkDiagram variant="sequence" />

A serves the agent and verifies the B attestation against B's metadata and JWKS. B does not mint an assertion in this flow. P2 verifies A's assertion against A's JWKS, signs a receipt with its B-attested key, and posts the receipt plus the exact attestation to A (or returns it for `identity_record_signup`). A verifies the B attestation and key, then attaches the receipt to your `/activity` audit trail.

## Try it as a developer

You need an MCP client that supports OAuth 2.1 and a browser for the consent step. There is no demo API key and no separate demo account.

1. Connect your coding tool to `https://agentregistrar.dev/mcp` and bind an agent during browser OAuth consent. If this is your first agent, follow the [Agent quickstart](/agents/quickstart/).
2. Ask the agent to sign up at **P1** (`https://verifiedprovider1.agentregistrardemorp.com`) using `identity_signup`. P1 is broker-managed and attested by A, so under the default `verify` policy it succeeds and returns a signed receipt you can record with `identity_record_signup`.
3. For **P2** (`https://verifiedprovider2.agentregistrardemorp.com`), open [agentregistrar.dev/trust](https://agentregistrar.dev/trust), expand **Advanced: federated broker trust**, add `https://agentregistrardemobroker.com` as trusted, and leave your policy at `verify`. Without that trust row, `verify` stops with `rp_broker_untrusted`. Under `strict`, P2 is also refused with `rp_attestation_mode_not_allowed` because P2 is provider-managed.
4. For **P3** (`https://unverifiedprovider1.agentregistrardemorp.com`), try signing up first under the default `verify` policy: it stops with `rp_unverified` and creates no acceptance or account. Then add a per-provider override in `/trust` setting P3 to `no_verify` and repeat: the signup proceeds without a signed receipt, and the terms acceptance still appears in `/activity`. Setting P3 to `blocked` refuses immediately with `rp_blocked`.

<Aside type="note" title="Trust is local policy">
Trusting Broker B does not make every B statement authoritative, and it does not make a provider safe. `verified` means the credential verified under your policy, not that the service is trustworthy.
</Aside>

### Policy outcomes for an unverified provider

| Policy | P3 result | What it proves |
| :--- | :--- | :--- |
| `no_verify` | Proceeds, shown as unverified; acceptance recorded in `/activity`, no signed receipt | Not a verification gate |
| `verify` (default) | Blocked with `rp_unverified`; no account, assertion, or acceptance | The default verification gate |
| `strict` | Blocked with `rp_unverified` | Broker-managed verification required; P3 has no source |
| `blocked` | Blocked with `rp_blocked`; applies to verified providers too | Separate human blocklist, always refuses |

Policy is set per human in [Developer Portal](/agents/portal/) (`/trust`); every agent under your account inherits your policy.

### Where to see the record

- Open `/activity` in the [Developer Portal](/agents/portal/) to inspect every terms acceptance joined with its strongest signup receipt (so keyless and unverified signups remain visible alongside signed receipts).
- Any provider account and API key are issued by the provider, never stored by Broker A.

## Inspect VaporCloud (reference provider)

[VaporCloud](https://skdl.dev) is a mock infrastructure provider selling fictional appliances so you can see the exact boundary between the identity-only protocol and vendor-specific APIs. It implements `v2.1.0` with broker-managed verification, signed receipts, a hash-pinned post-signup guide, and authenticated abuse reporting.

| Path | Purpose |
| :--- | :--- |
| [`/.well-known/agent-signup.json`](https://skdl.dev/.well-known/agent-signup.json) | Identity-only discovery document (`audience: "vaporcloud"`, `mode: "broker"`) |
| [`/api/signup/agent`](https://skdl.dev/api/signup/agent) | Brokered signup endpoint (`POST` with `Authorization: Bearer <jwt>`) |
| [`/terms`](https://skdl.dev/terms) | Provider-hosted terms fetched and SHA-256 hashed by the broker at signup |
| [`/docs/SKILL.md`](https://skdl.dev/docs/SKILL.md) | Hash-pinned vendor API guide (`context.url`), including key rotation and mock provisioning |
| [`/admin`](https://skdl.dev/admin) | Vendor-side admin view (vendor tooling, not protocol) |

Check VaporCloud's discovery conformance and broker-managed attestation with the validator:

```bash
pnpm --silent validate:discovery https://skdl.dev/.well-known/agent-signup.json \
  --json --probe-jwks --verify-attestation --require-attestation \
  --trusted-rp-broker https://agentregistrar.dev
```

Notice what VaporCloud keeps out of discovery: SKUs, quotas, provisioning endpoints (`/api/provision`), and credential rotation (`/api/account/rotate-key`) all live in `/docs/SKILL.md`, fetched and hash-verified only after signup.

## Try it as a provider implementer

You do not need an account, SDK, or shared secret to fetch discovery or verify an assertion. You cannot register your own provider on Broker B (it is operator-only for this demo). The three test discovery documents are public and served with `Cache-Control: no-store`:

- [P1 discovery](https://verifiedprovider1.agentregistrardemorp.com/.well-known/agent-signup.json)
- [P2 discovery](https://verifiedprovider2.agentregistrardemorp.com/.well-known/agent-signup.json)
- [P3 discovery](https://unverifiedprovider1.agentregistrardemorp.com/.well-known/agent-signup.json)

Validate all three from a checkout with the [validator](/protocol/validator/) installed:

```bash
# P1: A attestation, broker-managed
pnpm --silent validate:discovery \
  https://verifiedprovider1.agentregistrardemorp.com/.well-known/agent-signup.json \
  --json --probe-jwks --verify-attestation --require-attestation \
  --trusted-rp-broker https://agentregistrar.dev

# P2: B attestation, provider-managed
pnpm --silent validate:discovery \
  https://verifiedprovider2.agentregistrardemorp.com/.well-known/agent-signup.json \
  --json --probe-jwks --verify-attestation --require-attestation \
  --trusted-rp-broker https://agentregistrardemobroker.com

# P3: conformant, unverified
pnpm --silent validate:discovery \
  https://unverifiedprovider1.agentregistrardemorp.com/.well-known/agent-signup.json \
  --json --probe-jwks
```

P1 and P2 exit `0` with `valid: true` and a verified attestation (`mode: "broker"` for P1, `mode: "provider"` for P2). P3 exits `0` with `valid: true` and an unverified status. The validator reports conformance and attestation verification separately.

### Broker B documents

```bash
curl -sS https://agentregistrardemobroker.com/.well-known/agent-broker.json
curl -sS https://agentregistrardemobroker.com/.well-known/jwks.json
```

The metadata names the issuer, JWKS, attestation status endpoint, abuse endpoint, protocol versions, and contact (all same-origin, public Ed25519 keys in JWKS):

```json
{
  "issuer": "https://agentregistrardemobroker.com",
  "jwks_uri": "https://agentregistrardemobroker.com/.well-known/jwks.json",
  "attestation_status_uri": "https://agentregistrardemobroker.com/api/broker/attestation-status",
  "abuse_endpoint": "https://agentregistrardemobroker.com/api/broker/report-abuse",
  "protocol_versions": ["2.0"],
  "contact": "security@agentregistrardemobroker.com"
}
```

To read a signed status JWT for the current P2 attestation, extract `jti` from P2's attestation source and query Broker B:

```bash
URI="$(curl -sS https://verifiedprovider2.agentregistrardemorp.com/.well-known/agent-signup.json \
  | node -e 'let s="";process.stdin.on("data",d=>s+=d).on("end",()=>console.log(JSON.parse(s).attestation.uri))')"
JTI="$(curl -sS "$URI" \
  | node -e 'let s="";process.stdin.on("data",d=>s+=d).on("end",()=>{const p=JSON.parse(s).attestation.split(".")[1];console.log(JSON.parse(Buffer.from(p,"base64url")).jti)})')"
curl -sS "https://agentregistrardemobroker.com/api/broker/attestation-status?jti=${JTI}"
```

The response is `{attestation_jti, status_jwt}`. The status JWT names the attestation in `sub`, reports `active`, `suspended`, or `revoked`, and expires in at most five minutes.

### Synthetic receipt shape

A signup receipt is a compact JWS signed by the provider's key. The decoded claims below are illustrative only and use synthetic values:

```json
{
  "iss": "https://verifiedprovider1.agentregistrardemorp.com",
  "sub": "agt_demo_example",
  "aud": "https://agentregistrar.dev",
  "jti": "srp_demo_example",
  "iat": 1794009600,
  "assertion_jti": "jti_demo_example",
  "service": {
    "audience": "demo-verifiedprovider1",
    "origin": "https://verifiedprovider1.agentregistrardemorp.com",
    "provider_name": "Demo Verified Provider 1",
    "provider_url": "https://verifiedprovider1.agentregistrardemorp.com",
    "account_id": "acct_demo_example",
    "attestation_jti": "rpa_demo_example",
    "key_id": "rp_example_1"
  },
  "agent": {
    "id": "agt_demo_example",
    "name": "demo-agent",
    "email": "demo-agent@agents.example"
  },
  "human": {
    "id": "hum_demo_example",
    "name": "Example Owner",
    "email": "owner@example.com",
    "verified": true
  },
  "tos": {
    "version": "demo-2026-11-07",
    "url": "https://verifiedprovider1.agentregistrardemorp.com/terms",
    "sha256": "sha256:<64 hex characters>"
  },
  "context": {
    "url": "https://verifiedprovider1.agentregistrardemorp.com/guide",
    "sha256": "sha256:<64 hex characters>"
  },
  "signed_up_at": "2026-11-07T00:00:00Z"
}
```

`context` is optional; when present it points to the provider's guide and is hash-pinned (the agent fetches and checks it, never the broker). A receipt carries no expiry and remains verifiable against the historical attestation snapshot it names. The provider can post `{signup_token, rp_attestation}` directly to `https://agentregistrar.dev/api/broker/signup-receipt` (`rp_callback`), or the agent can submit it via `identity_record_signup` (`rp_signed`). Both carry the same cryptographic proof. Do not post the synthetic example; unsigned or mismatched receipts are rejected.

### Rotation and renewal

Broker and provider key rotation, renewal, suspension, and rollback are operator drills, not public actions. Expected behavior across the live network:

- An attestation lives for 24 hours. Broker A renews P1's broker-managed token on demand; P2 renews its provider-managed token on a 12-hour target, and expiry is its revocation bound.
- New broker keys publish with overlap so existing attestations stay valid until expiry.
- Brokers and providers cache JWKS for at most five minutes.
- A suspended broker-managed attestation stops new lookups within five minutes under `verify` or `strict`; a suspended provider-managed attestation may stay accepted until it expires.
- Historical receipts remain verifiable through the attestation snapshot they reference.

## What you can and cannot test

| You can test | You cannot test |
| :--- | :--- |
| Discovery conformance, Broker B metadata/JWKS/status, and attestation verification for P1, P2, P3, and VaporCloud | Registering an agent with Broker B (B is an RP-only demo broker) |
| Same-broker signup at P1 and VaporCloud with your Broker A agent | DNS/browser isolation across P1, P2, and P3 (they share `agentregistrardemorp.com`) |
| Cross-broker signup at P2 after trusting Broker B in `/trust` | Multi-broker governance or third-party federation agreements |
| Unverified `no_verify`, `verify`, `strict`, and `blocked` outcomes at P3 | Anonymous admin actions, key rotation, or destructive drills |
| Receipt ingestion, dedupe, `/activity` records, and the [abuse-reporting contract](/providers/guides/abuse-reporting/) | Signed abuse reports without a provider signing key; production SLA or security reviews |
| Assertion verification with public JWKS, no account or SDK | Catalogs, billing, or infrastructure resale |
